# TM2-75 · deploy · backups must include paper_bot_data
Branch: tm2/TM2-75        Base: main        Owner: TM2

## Finding
`deploy/backup.sh:13` hard-codes `VOLUMES=(openalgo_db openalgo_log openalgo_strategies openalgo_keys trade_mcp_data)`. The `paper_bot_data` volume, added by PB-2, holds every paper decision and trade, and it isn't backed up. restore.sh doesn't cover it either.

## Files you may touch
- `deploy/backup.sh`
- `deploy/restore.sh`
- `docs/backup.md`
- `deploy/test_tm2_75_backup_volumes.py` (new)

## What to build
- Add `paper_bot_data` to the backup and restore set.
- SQLite consistency: back up while the bot may be writing in WAL mode. Pick one approach and document it in docs/backup.md:
  - run `sqlite3 .backup` inside the container;
  - or stop paper-bot during the copy;
  - or copy `paper.db` together with `paper.db-wal` and `-shm`, keeping them together.
- Leave `caddy_data` out (certs regenerate), and say so in the docs.
- Add a guard test: every named volume in `docker-compose.yml` is either in VOLUMES or on an explicit `EXCLUDED_VOLUMES` list with a reason. Future volumes then can't be silently missed.

## Acceptance criteria
- The guard test fails if a new compose volume is added without being classified.
- A backup/restore round-trip of a populated paper.db (fixture) in a temp Docker env (skip if no docker) gives the same row counts.
- Existing backup tests stay green.

`uv run --with pytest --with pyyaml pytest -q deploy/`
