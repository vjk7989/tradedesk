# TM2-47 · deploy · container memory/CPU limits as the last line of defence
Branch: tm2/TM2-47        Base: main        Owner: TM2

## Why
ADR-18 bounds each sandbox run (memoryBytes + 16 MB), and O-10 caps concurrent runs (EXECUTE_MAX_CONCURRENT, default 4). No service has a container memory limit, though, so a bug in any layer can still take the whole VPS down, including OpenAlgo and the broker session. Add Docker resource limits so a runaway trade-mcp or bt-service is OOM-killed and restarted on its own, without starving OpenAlgo.

## Files you may touch
- `deploy/docker-compose.yml`: `mem_limit` (and `cpus` if you judge it useful) per service, from env with defaults. For example: `mem_limit: ${TRADE_MCP_MEM_LIMIT:-768m}`.
- `deploy/.env.example`: the new vars, with a sizing comment. trade-mcp ≈ base + EXECUTE_MAX_CONCURRENT × ~80 MB (ADR-18). bt-service needs headroom for pandas backtests; measure a typical walk-forward. OpenAlgo gets its upstream recommendation, or none if there isn't one.
- `docs/vps-runbook.md` §1/§5: sizing guidance for a 4 GB VPS.
- `deploy/test_tm2_47_limits.py` (new)

## What to build
- Pick defaults that fit the runbook's minimum 4 GB VPS, leaving about 1 GB for the OS and Caddy.
- `restart: unless-stopped` already exists. Confirm that an OOM-killed service restarts.

## Acceptance criteria
- `docker compose config` resolves the limits. Defaults apply when unset, and overrides pass through.
- The sum of the default limits is ≤ 3 GB.
- The trade-mcp default is ≥ base + 4 × 80 MB. Measure the base RSS and put it in the report.
- Existing deploy tests stay green. If a pinned compose key-set test changes, that's an AC change for your test writer.

## Verify
`uv run --with pytest --with pyyaml pytest -q deploy/`, plus CI. The deploy job has Docker.
