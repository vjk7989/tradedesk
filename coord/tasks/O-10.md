# O-10 · trade-mcp · cap concurrent `execute` runs
Branch: own/O-10        Base: main        Owner: OWNER        Priority: HIGH (DoS)

## Why
Each `execute` run can use about memoryBytes (64 MB) + 16 MB of WASM headroom + host overhead (ADR-18). Nothing limits concurrency, so a token holder (or a prompt-injected AI issuing parallel tool calls) can run N at once: 50 × ~80 MB ≈ 4 GB on the VPS.

## Files you may touch
- `trade-mcp/src/server.ts`: the `execute` tool handler only.
- `trade-mcp/src/config.ts`: add one env var, `EXECUTE_MAX_CONCURRENT` (integer 1..32, default 4). Follow the existing `EXECUTE_TIMEOUT_MS` parsing and clamp style exactly.
- `trade-mcp/test/o10_execute_concurrency.test.ts` (new)
- Put the lines for `deploy/.env.example`, the compose env and the runbook in your report. Don't edit them; the owner adds them in a follow-up, so the deploy pinned tests are touched once.

## What to build
- A process-wide counter of in-flight `execute` runs.
- When the counter is at the limit, a new call fails at once (no queueing) with `{ ok: false, error: "busy: too many concurrent executes, retry shortly" }`, in the same response format as the existing errors.
- The slot is always released: on success, error, timeout, or a thrown exception (use `finally`).
- `search` is unaffected.
- The read-only and full scopes share the same limit.

## Acceptance criteria
- Use fake sandbox runs that block on a promise. N+1 concurrent calls give exactly N runs and 1 busy.
- Slots free after each kind of exit: ok, throw, timeout.
- Env parsing: unset gives 4. 0, 33, -1, `abc`, `1.5` and an empty string follow the `EXECUTE_TIMEOUT_MS` rule (clamp, or fall back to the default; match that code exactly).
- Existing tests stay green. Only pinned config key-set tests may need the test writer's update; list them.

## Verify
`cd trade-mcp && npm ci && npx vitest run && npx tsc --noEmit && npm run build`, plus CI.
