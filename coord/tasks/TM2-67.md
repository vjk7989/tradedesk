Branch: tm2/TM2-67        Base: main        Owner: TM2        Approved: owner 10:17 IST

## Finding (TM2-60 follow-up 1)
`enrich_price_frames_with_fundamentals` in `bt-service/vibe_bt/backtest/loaders/tushare_fundamentals.py` raises `pandas.errors.MergeError` when a price frame has a tz-aware DatetimeIndex. The PIT dates are naive and the bar keys are tz-aware. This happens on main too (it predates TM2-60), and `bt-service/tests/test_tm2_60_datetime_columns.py` pins it as a strict `xfail(raises=MergeError)`.

## Files you may touch
- `tushare_fundamentals.py`. Your test writer flips the strict xfail in `test_tm2_60_datetime_columns.py` into real assertions.

## What to do
- Build the merge key from a naive wall-clock date in the market's timezone: for a tz-aware index, `tz_convert("Asia/Shanghai")` (A-share PIT dates are CN-local dates), then `tz_localize(None)`, `.normalize()` and `.as_unit("ns")`. Naive indexes behave exactly as today.
- The returned frame keeps the caller's original index (same tz, same unit, same values). Only the internal key is converted.
- The `subdaily="next_day"` rule must hold in CN-local time. A UTC bar at 2024-02-29 23:30Z is 03-01 07:30 CST, so the 03-01 rule applies.
- Check the other datetime-joining loaders TM2-60 covered (industry, rsshub, `_ffill_pit`) for the same tz-aware failure. Fix it there only if it's the same small pattern; otherwise report it.

## Acceptance criteria
- A tz-aware index (UTC and Asia/Shanghai, in each of the s/ms/us/ns units) gives the same values as the equivalent naive CN-local index. The output index is identical to the input.
- The strict xfail becomes a passing test, and there's a pre-fix failure proof.
- Results for naive indexes are byte-identical to main.
- No new warnings.
