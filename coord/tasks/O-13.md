# O-13 · trade-mcp · why the in-run memory check misses a JSON.parse loop
Branch: own/O-13        Base: main        Owner: OWNER        Priority: MEDIUM (security hardening)

## Finding (O-12 Part B)
A guest loop of large `JSON.parse` calls at a 16 MB cap completes inside the guest. The memory error only comes from the post-run WASM heap check (ADR-18 layer 2). Neither the QuickJS `setMemoryLimit` nor the interrupt-time ceiling check fires during the run. Host growth is still bounded by the post-run check and the 64-slot/1 MB caps, but the in-run guard should catch it.

## Files you may touch
- `trade-mcp/src/sandbox/quickjs.ts`
- `trade-mcp/test/o13_inrun_memory.test.ts` (new)

## What to do
1. **Reproduce and measure.** Record the guest heap (`runtime.computeMemoryUsage()` / `dumpMemoryUsage()`, if available) and the WASM memory size before, during and after a parse loop. Answer three questions:
   - Is the QuickJS memory limit accounting these allocations?
   - Does the interrupt handler run often enough? It is called every N bytecodes, and a loop of a few large native calls runs few bytecodes.
   - Is the growth in the WASM heap from malloc fragmentation rather than live objects?
2. **Fix it so the run fails during execution, not only after.** Candidates:
   - check the ceiling inside the interrupt handler on every call, which is cheap: `getWasmMemory().buffer.byteLength`;
   - set the interrupt to fire more often;
   - check the WASM size in each binding call and after each top-level microtask pump.

   Choose the simplest one that makes the test fail fast. Measure its overhead on a normal script (it must be under 5% slower) and report it.
3. Explain the root cause in the report.

## Acceptance criteria
- The parse-loop test fails during the run, before it completes. Prove this with a side-effect log: the guest logs after each parse, and the log must stop early.
- The host's peak memory stays within the ceiling.
- All existing sandbox, O-8 and O-9 tests stay green and unedited.
