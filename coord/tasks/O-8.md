# O-8 · trade-mcp · SECURITY: sandbox memory cap must cover ArrayBuffer/TypedArray allocations
Branch: own/O-6 (PR #57; the failing REPORT test is already there)        Owner: OWNER        Priority: HIGH

## Finding (from the O-6 investigation)
`runtime.setMemoryLimit(memoryBytes)` (src/sandbox/quickjs.ts) does not count ArrayBuffer/TypedArray backing stores. With a 4 MB cap, 256 × 1 MB Uint8Arrays succeed, and old test loops reached about 2 GB in the trade-mcp host process.

Any `execute` caller, including a prompt-injected AI, can exhaust host memory and crash the process that holds the broker session. The REPORT test in PR #57 fails 20 out of 20 times.

## Files you may touch
- `trade-mcp/src/sandbox/quickjs.ts`
- `trade-mcp/test/o8_sandbox_buffers.test.ts` (new)

## What to build (defence in depth, both layers)
1. **Remove the binary-buffer surface.** Before user code runs, delete or overwrite these globals in the context:
   - `ArrayBuffer`, `SharedArrayBuffer`, `DataView`, `Atomics`;
   - every TypedArray constructor (`Int8Array` … `BigUint64Array`, `Float32/64Array`, `Uint8ClampedArray`);
   - `WebAssembly`, if present.

   Also make sure they can't be reached another way: through the prototype of a typed array returned by any binding (bindings return JSON, so check this), or through `globalThis` aliases. Trading and backtest scripts don't need them.
2. **Hard ceiling on the WASM heap.** Each run creates its own module with `newQuickJSWASMModule()`. In the interrupt handler, which already checks the deadline, also check the module's WASM linear-memory size. Use `getWasmMemory()` or the equivalent in quickjs-emscripten 0.32; read its typings in node_modules. Interrupt with the error `memory limit exceeded` once it goes past `memoryBytes + 32 MB` of headroom.

   If no memory accessor exists, find the supported way to cap or observe the module's memory, and document what you chose. Don't add a dependency without asking.
3. The error text for both layers must match `/memory/i`, so the existing memory tests' positive match holds.

## Acceptance criteria
- The PR #57 REPORT test (Uint8Array control pair) passes.
- Your test proves that `new Uint8Array(1e6)`, `new ArrayBuffer(…)`, `new DataView`, `Atomics` and `WebAssembly` are unavailable or throw.
- A loop that allocates objects and strings past the cap still ends with a memory error within the timeout. The host stays alive and the next run works.
- Normal scripts are unaffected: the existing sandbox, sdk and server tests pass unedited, apart from any pinned test that asserted typed arrays exist. If there is one, list it; the test writer updates it.

## Verify
`cd trade-mcp && npm ci && npx vitest run && npx tsc --noEmit && npm run build`. CI must also be green.
