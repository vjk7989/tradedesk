# TM-10 · trade-mcp · let long backtests (walkForward) finish inside `execute`
Branch: tm/TM-10        Base: main **after TM-3 is merged** (TM-3 also edits `src/config.ts`)        Owner: TM1

## Problem (found by TM1 in TM-9)
`execute` runs with `executeTimeoutMs` defaulting to 60 s (`src/server.ts`), but `/walkforward` allows 600 s server-side. A realistic walk-forward through `execute` times out while bt-service keeps running and holds its single slot.

## Files you may touch
- `trade-mcp/src/config.ts`: add `EXECUTE_TIMEOUT_MS` only.
- `trade-mcp/src/server.ts`
- `trade-mcp/src/sdk/api-docs.ts`: one sentence in the walkForward and backtest docs.
- `docs/connect-clients.md`: a short note on client tool timeouts.
- New: `trade-mcp/test/tm10_execute_timeout.test.ts`.

## What to build
1. Env `EXECUTE_TIMEOUT_MS`: default 60000, clamped to [5000, 900000]. A non-integer value falls back to the default. It is passed as `executeTimeoutMs` to `createMcpServer` from `index.ts`, or read in `server.ts`, whichever is smaller. If you need to touch `index.ts`, it is allowed.
2. The walkForward client's own timeout (660 s) must not exceed the execute timeout in a way that leaves orphan work. Document in api-docs that for walk-forward runs the operator should set `EXECUTE_TIMEOUT_MS` ≥ 660000. Also say that MCP clients may have their own tool-call timeout, so check your client's setting.
3. Leave `.env.example` and compose alone; deploy files are another task.

## Acceptance criteria
- Values 4999, 5000, 900000, 900001, "abc", "" and unset give the clamped value or the default.
- A sandbox run longer than the configured timeout returns a timeout error. Test this with a tiny configured value and an injectable timer.
- The default stays 60 s.
- Existing tests stay green.

cd trade-mcp && npx vitest run && npx tsc --noEmit && npm run build
