## What to build
A concise security policy and threat model, built from the code and the ADRs. Every claim must cite a file or ADR in your report.
1. **Reporting.** Ask for private disclosure through GitHub Security Advisories ("Report a vulnerability"). No email addresses. Say it's a personal project with no SLA.
2. **Scope and assets.** The broker session and API keys, the OpenAlgo key, `MCP_TOKEN` and the read-only token, OAuth tokens, the audit log.
3. **Threat model and controls, one line each:**
   - Untrusted AI-written code runs through `execute`. Controls: QuickJS sandbox, no network or fs, the ADR-18 memory, buffer and binding caps, O-10 concurrency, O-13 in-run checks once merged, and the code-size cap.
   - Prompt injection leading to trading. Controls: server-side risk engine (ADR-5): caps, market hours, holidays, the kill switch, the optional short-option cap, `semi_auto`, paper default, read-only token.
   - Credential leakage. Controls: audit redaction by key, plus the value scrub in `audit.recent`. Secrets are never in responses (readyz, dry-run, check, history).
   - The network. Only Caddy is exposed and trade-mcp's port is never published. Static-IP broker registration. OAuth: PKCE, a DCR allowlist, refresh rotation with family revocation, revoke-all.
   - Supply chain. SHA-pinned actions, Dependabot with no auto-merge, lockfiles generated with the pinned uv.
4. **Known limits (accepted).** Single process per DATA_DIR. The sandbox is not a hard security boundary against a QuickJS or WASM zero-day; run it on a dedicated VPS. Live trading needs the operator's own checklist (runbook §10).

## Acceptance criteria
- ≤150 lines. No secrets, no hostnames, no personal data.
- Every control named exists in the code. The reviewer greps each one.
