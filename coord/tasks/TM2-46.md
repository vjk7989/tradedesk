# TM2-46 · trade-mcp · DATA_DIR lock so oauth:revoke-all can't run against a live server
Branch: tm2/TM2-46        Base: main        Owner: TM2

## Why
TM2-35's edge tests proved that revoking while trade-mcp runs gets undone, because the live server persists its in-memory tokens again. `--force` exists for the stopped-container `docker compose run` flow, so an operator can still misuse it against a live server.

## Files you may touch
- `trade-mcp/src/index.ts` (startup and shutdown only), or a new `trade-mcp/src/datadir-lock.ts`
- `trade-mcp/src/oauth/revoke-cli.ts`
- `trade-mcp/test/tm2_46_datadir_lock.test.ts` (new)

## What to build
- On start, trade-mcp creates `DATA_DIR/trade-mcp.lock` with its pid and start time, using exclusive create.
  - If a lock exists and its pid is alive, refuse to start with a clear message.
  - If the pid is dead, the lock is stale: replace it and log that.
- On clean shutdown (the existing signal handlers), remove the lock.
- `revoke-cli` checks the lock. If its pid is alive, refuse even with `--force`, saying "trade-mcp is running; stop it first". `--force` then only skips the stale-lock case.
- In containers the pid namespace differs (pid 1). Document how the check behaves for the `docker compose run --rm --no-deps` flow: a different container means a different pid namespace. Either use a start-time plus hostname heuristic, or rely on the lock plus `docker compose ps`, and state the limit honestly in the report.

## Acceptance criteria
- Tests cover:
  - double start is refused;
  - a stale lock is replaced;
  - a clean shutdown removes the lock;
  - the CLI refuses while the lock is live;
  - the CLI proceeds on a stale or missing lock.
- Existing tests stay green and unedited.

## Verify
