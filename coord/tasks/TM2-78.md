# TM2-78 · deploy/docs · scheduled off-site backups to Google Cloud Storage
Branch: tm2/TM2-78        Base: main **after #119 (TM2-75) merges**        Owner: TM2

## Why
The live stack runs on a single GCP VM. `deploy/backup.sh` writes local archives, and docs/backup.md mentions off-site rsync. On GCP the natural off-site target is a GCS bucket.

## Files you may touch
- `deploy/backup-gcs.sh` (new): a thin wrapper that runs backup.sh, then uploads to `gs://$BACKUP_BUCKET/` with `gcloud storage cp`, keeping N days.
- `docs/backup.md`: a GCS section.
- `docs/gcp-deploy.md`: one step.
- `deploy/test_tm2_78_backup_gcs.py` (new)

## What to build
- **Setup documentation:**
  - creating the bucket (same region, uniform access, a retention/lifecycle rule deleting after N days);
  - a VM service account with only `roles/storage.objectCreator` on that bucket;
  - a systemd timer or cron entry for a daily run at 02:30 IST.
- **Encryption:** backups contain secrets (`.env`, `openalgo.env`), so encrypt before upload using `age` or `gpg` with a public key. The private key stays off the VM. Document this.
- **Restore drill:** download, decrypt, then `restore.sh`.

## Acceptance criteria
- The script fails fast without BACKUP_BUCKET or a recipient key.
- It never uploads unencrypted. Test this with a fake `gcloud` on PATH that records its arguments.
- It deletes local temp files afterwards.
- `bash -n` passes, and the existing backup tests stay green.
