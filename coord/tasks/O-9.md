## What to build
1. **Fail closed on the removed globals.** After deleting them, check from inside the guest that each name is `undefined` on `globalThis`. If any is still present, because a non-configurable property survived the delete, fail the run with "sandbox init failed" before user code runs.
2. **Measure argument size in the guest first.** Before `vm.dump` / `JSON.stringify` on the host, measure the argument size inside the guest: a guest-side `JSON.stringify(arg).length` wrapper, or an equivalent that runs under the guest memory limit. Reject above 1 MB without ever building the host copy. Keep the host-side check as a second check.
3. **Cap binding results going back into the guest.** Before `newString`, if the stringified result is over a cap (default 4 MB, or `memoryBytes/4` if that is smaller), reject the guest promise with "binding result too large". Say so in the error, so the AI can narrow its query, e.g. fewer bars or a shorter date range.
4. **Fix handle and dispose leaks.**
   - Dispose `jsonParse`.
   - Make `disposeQuietly` dispose the runtime even if `vm.dispose()` throws.
   - Add a loop test: 200 runs, mixing hostile and normal, with RSS and `external` flat within a stated tolerance.
5. **Heap ceiling.** Document the +16 MB choice in a code comment and the report. The brief said +32 MB; the developer measured that 16 MB is enough and tighter. Also check the ceiling when a binding settles (before resuming the guest), not only in the interrupt handler.

## Acceptance criteria
- Every item above has a test.
- Normal scripts, the existing sandbox, sdk and server tests, and the O-8 edge tests stay green and unedited.
- If a large-data binding (`market.history` over a long range) can now hit the result cap in a realistic query, list it. The cap must not break normal use: a year of daily bars must fit.
