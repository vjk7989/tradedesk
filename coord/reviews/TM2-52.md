# TM2-52 review (PR #90)
Verdict: APPROVE WITH FOLLOW-UPS (no blocker). Scope is clean: one test, its helpers, and the report. No src change and no other test touched. No skip. The 5000-parsed, NSE-open and added-holiday-closes asserts are kept (test:255-258).

## Findings
- HIGH trade-mcp/test/tm3_holidays.edge.test.ts:229 - `process.threadCpuUsage()` on Windows. Node implements it with GetThreadTimes, which has roughly 15.6 ms tick granularity. The small workload costs about 2.5-30 ms of CPU (500 checks; parse of 250 dates is about 1 ms). The median of 5 small runs can read 0 or 15.6 ms. With 0, `Math.max(small, 0.05)` (line 248) turns the ratio into hundreds and the test fails. With 15.6 ms, the ratio swings by 2x either way. Windows is a stated target, so this is a likely new flake. The report only measured on Linux. Fix: size the small workload so it costs at least about 200 ms CPU, or fall back to a larger N on win32, or use `performance.now()` with min-of-N.
- MEDIUM :229 - `process.threadCpuUsage()` was added in Node 23.9 and 22.19. CI uses `node-version: 22`, which resolves to the latest 22.x and works. package.json `engines` allows `>=22`, so an older 22.x throws a TypeError. Guard it (`typeof process.threadCpuUsage === "function"`, else use `process.cpuUsage()` or wall-clock) or raise `engines`.
- MEDIUM :274 - The checks ratio varies the call count (500 vs 10k) against a fixed 5000-entry list. It catches a per-call regression, such as a cache that grows. It does not catch isMarketOpen becoming O(n^2) in list length, because that cost is the same at both sizes. Only the parse ratio (250 vs 5000 dates) varies list length. The O(n^2) proof was done only on the checks workload with a synthetic accumulating `seen` array. It is credible for that shape (115x, 97x, 95x, all above 30), but no parse O(n^2) was demonstrated. The measured parse ratio is 8.5-18x, so the 30x bound is loose there. A quadratic parse would be about 400x, so it would still be caught.
- LOW :227 - The margin is 30 vs 21.5 measured max (1.4x headroom) on the checks side. That is thin but acceptable, because the CPU-time medians were tight (18.9-21.5 over 25 loaded runs). The other side has large room: quadratic is about 100x in the proof and 400x in theory. Median-of-5 for checks is modest. A single GC pause or major collection in the large run costs about 1-3 ms against roughly 600 ms of CPU, so the effect is small. The small run is about 30 ms, so one 3-5 ms scavenge is a 10-15% swing. A median of 5 absorbs one outlier but not two. Raising checks reps to 9 would be cheap. Thread CPU does not include concurrent GC or JIT helper threads, which helps. The `isMarketOpen` call is allocation-light.
- LOW :276 - The 60 s timeout is justified. The test now runs about 4 s alone and 13 s under load because of reps and warm-up. The old default 5 s timeout would have flaked. A 60 s limit is generous but harmless, since the ratio is the real guard. The test is about 7x slower than before.
- INFO :229 - Per-thread correctness. threadCpuUsage reports the calling thread. The vitest 5 default pool is forks (child process main thread) and threads (a worker) also works. The test body is synchronous, so it runs entirely on the measured thread. It measures the right thing, excluding descheduling.
- INFO - Acceptance: 20 of 20 loaded runs passed, and the O(n^2) proof is recorded in the report (3 of 3 failures with the message showing the ratio). The cause analysis is accurate, since includes() on 5000 entries is O(n) per check.
- INFO coord/reports/TM2-52.md - The report notes an unrelated tm2_46_datadir_lock failure under load. It is out of scope but worth a task.
