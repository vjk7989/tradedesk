## 2. Findings

**MEDIUM-1. sync_holidays: wrong URL choice, and it is out of order.**
- Caddyfile does publish `openalgo.{$DOMAIN}`. It reverse-proxies the whole OpenAlgo app with no Caddy-level auth; the only auth is OpenAlgo's own (API key in the POST body, TLS-protected).
- Routing an operator script out to the public internet and back works, because the script accepts https. It also needs DNS and certificate issuance to be done. It depends on the VM resolving its own public IP (hairpin; works on GCP), and it puts the real API key through the public path and the shell env or history for no reason.
- The script is stdlib-only Python and already treats `http://openalgo` as a trusted local host (sync_holidays.py line 60 warns on plain http to other hosts). So it was designed to run in-network.
- **Recommend running it inside the compose network.** `bt-service` is a Python image on the internal network whose env already holds `OPENALGO_URL=http://openalgo:5000` and `OPENALGO_API_KEY`:
  `docker compose run --rm --no-deps -v "$PWD:/work" -w /work bt-service python sync_holidays.py --risk risk.json [--dry-run]`
  I have not tested this. The container runs as uid 1000 (`app`), and the script writes a temp file, `.bak` and `os.replace` in the mounted dir. So the dir must be writable by uid 1000; otherwise it fails. The runbook should say that. Keep the public URL only as a fallback.
- Ordering: the paragraph sits in §5, but it needs the stack up (§6) and the real API key (§7). On a first deploy it cannot run in §5. Say "after section 7 (or any time later)".
- `docs/holidays.md` still shows `OPENALGO_URL=http://127.0.0.1:5000`, which contradicts the runbook (INFO; out of scope for this PR but worth a follow-up).

**MEDIUM-2. `chmod 600 openalgo.env` bind mount: unknown whether the container can read or write it.**
- Compose bind-mounts the host file at `/app/.env`, and host uid and mode carry through. The OpenAlgo image user is not visible (vendor is absent), and the report says it was "not checked" while the runbook is silent. If the container user's uid differs from the operator's, 600 means OpenAlgo cannot read the file, and the stated "writes secrets back on first run" fails too. It works only if the uids happen to match (often 1000 on a fresh GCP VM).
- The runbook should say this is unverified and add a check after first start:
  `docker compose exec openalgo sh -c 'id; test -r /app/.env && echo readable'`
  with the remedy: `chown` the file to that uid, or relax to 640 with a matching group.
- Also consider that the runbook never states that OpenAlgo needs to write the file; a read-only failure would look like a crash loop.

**LOW-1. §13 `sleep 15` is borderline; use 20.**
- Liveness is `ageMs < 15000` (datadir-lock.ts:74; revoke-cli.ts prints "wait 15 s"), so age >= 15 s counts as stale. The heartbeat is every 5 s. After `compose stop` returns, lock age is somewhere in 0-5 s (zero if the final heartbeat was just before exit), plus `docker compose run` start-up of a second or so. So 15 usually passes, but a worst case lands right at the edge.
- A 16 would be correct but thin. I recommend `sleep 20`, which is the same semantics with margin, and costs nothing.
- If revoke exits 4, the `&&` chain leaves trade-mcp STOPPED. The runbook should tell the operator to wait and rerun, then `docker compose start trade-mcp`. The failure mode is safe (fail closed), just surprising.

**LOW-2. §5 lint-before-start wording.** The `docker compose run ... trade-mcp node dist/src/risk/lint.js` candidate form triggers an image build in §5 (before §6). It is fine, but it will take minutes on first use; say so. The `docker compose exec` form only works after §6.
