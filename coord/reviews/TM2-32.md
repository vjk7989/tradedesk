# TM2-32 review (PR #61)

Verdict: APPROVE (no blockers). The 5 red pinned TM2-25 tests are expected and need the test writer's update before merge.

## What I checked
- Diff scope: search.ts changes only the Rules selection (`search.ts:29-39`). Entries matching, the 20 cap, the readonly filter, the empty-query path, the miss message and the block format are untouched.
- Score: `distinct = [...new Set(tokens)]`, then count of distinct tokens that are case-insensitive substrings of the lowercased line. A repeated token counts once. Score 0 is filtered out.
- Selection: sort by score desc then header index asc, take 8, re-sort by index. Output is in header order. Tie-break is explicit on index, so it is deterministic and does not depend on sort stability.
- Perf: the header is 9 lines, so per-query cost is negligible. No pathology.
- Empirical (temp worktree, 63 pinned queries x 2 scopes + extras; nothing committed): 
  - Whenever 8 or fewer header lines match, output is byte-identical to main (TM2-25). 120 of 126 outputs are byte-identical; the 6 that differ are "e maxShortOptionQtyPerOrder", "e e e maxShortOptionQtyPerOrder" and "a e i o u", in both scopes.
  - Output with the Rules block stripped equals main's output for all 126 cases, so entries never changed.
  - An independent ranking oracle matched the implementation on every >8-match query.
  - Readonly never renders a trade entry; the 20 cap held.
  - Because the header has 9 lines, ranking only changes output when all 9 lines match (>8). Queries of a single token still get the first 8.

## The 5 failing TM2-25 edge tests (tm2_25_search_header.edge.test.ts)
All five fail only because of the intended ranking change:
- "cap is by header order ... drops the cap line": asserts the cap line is absent; now present. This is the AC.
- "full/readonly: Rules block is exactly the first 8 matching header lines": the loop breaks at the first mismatch, "e maxShortOptionQtyPerOrder"; the rules are now the ranked 8, the others are unaffected.
- "full/readonly: compatibility with main": the first mismatch is the same query. I verified separately that the entries part (after the Rules block) is identical to main's for every query in the list; only the Rules block differs.
Note: these loops break on the first failure, so the updated tests should also cover the later queries ("a e i o u" style) once rewritten.
