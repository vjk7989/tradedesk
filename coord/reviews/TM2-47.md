## Findings

### HIGH
1. **Brief deviation: OpenAlgo gets an unmeasured 1g limit** (deploy/docker-compose.yml:23, deploy/.env.example OPENALGO_MEM_LIMIT, docs/vps-runbook.md:42). The brief says "OpenAlgo gets its upstream recommendation, or none if there isn't one". The developer found none (reported honestly) but set a limit anyway, and the .env.example comment claims 1g "covers the Flask app, websocket proxy and its 512 MB shm_size" with no measurement. shm is charged to the container cgroup, so 512 MB of shm plus Python leaves little headroom. OpenAlgo holds the broker session, and an OOM kill there is exactly the trading disruption the task exists to prevent.
   Recommendation: follow the brief. Ship OpenAlgo with no default limit, and keep `OPENALGO_MEM_LIMIT` as an opt-in override, for example by adding the line only in a commented example or using a conditional. The other three services are capped at 1920 MB, so they cannot starve OpenAlgo, and a 4 GB host keeps about 2 GB for OpenAlgo and the OS. A runaway OpenAlgo then only threatens itself. If the owner prefers a ceiling, it must come from a measured peak (with shm in use) plus margin, and the AC "sum <= 3 GB" must be restated, since a larger OpenAlgo limit breaks it. The deviation should be an explicit owner decision, and the report should list it as one.

### MEDIUM
2. **trade-mcp worst case is slightly understated** (deploy/.env.example comment; docs/vps-runbook.md:42). The formula (ADR-19) is 100 + 4 x (64 + 32) = 484 MB and the arithmetic checks out: memoryBytes default 64 MiB (trade-mcp/src/sandbox/quickjs.ts:51), EXECUTE_MAX_CONCURRENT default 4 (compose and config.ts:107). ADR-18 also allows up to memoryBytes of pending host-side binding argument bytes per run, which is not in the 96 MB per run. Adding that gives roughly 100 + 4 x 160 = 740 MB, close to the 768m limit. The limit is still the intended last resort, and the developer only measured light workloads (212 MB peak), but the "~284 MB headroom" claim is optimistic. Either state this in the sizing note or raise the default to 896m (sum 3072 MB, still <= 3 GB only if OpenAlgo is not capped per item 1).
3. **Acceptance criteria "defaults apply when unset, overrides pass through" are not exercised against `docker compose config`** (deploy/test_tm2_47_limits.py). The new tests are static YAML and regex checks (good value: sum <= 3 GB, 484 MB floor, env/compose default consistency, restart policy, no trade-mcp ports). The existing `cfg` fixture resolves with `--env-file .env.example`, so it never tests unset defaults or an override. Add one docker-gated test (or a CI step) running `docker compose config` with no env file and with `TRADE_MCP_MEM_LIMIT=512m`. `BASE_RSS_MB = 100` is a hard-coded constant, so the 484 MB test only guards the formula, not reality.

### LOW
4. docs/vps-runbook.md:41 still says each execute run "can use about 80 MB" while the new paragraph at line 42 says 96 MB. deploy/.env.example (line 13 comment) says "+ 16 MB WASM headroom (ADR-18)" while the new text says 32 MB (ADR-19). Align both.
5. docs/vps-runbook.md:42 sits between the .env paragraphs and the "Edit `openalgo.env`:" bullet list, which splits the flow. It is also a long single paragraph; consider a short §5 subsection.
6. bt-service `tmpfs: /runs` is charged to the same 1g cgroup. Run artefacts count toward the limit. Peak 282 MB leaves margin; worth a sentence.
7. `mem_limit` without `memswap_limit`: on hosts with swap accounting enabled a container can use swap beyond its limit, delaying the OOM kill. Consider noting it or setting `memswap_limit` equal to `mem_limit`.

### INFO (verified OK)

No ports published beyond Caddy's 80/443; trade-mcp still uses `expose` only.

Compose does not pass BT_MAX_CONCURRENCY, so the worst case is one run at a time: 282 MB measured vs 1g is fine. If someone later exposes BT_MAX_CONCURRENCY, the limit must scale (about 300 MB per run plus the parent).
- Caddy 128m is fine for two vhosts at this traffic.
- Total: 768 + 1024 + 1024 + 128 = 2944 MB <= 3072 MB; about 1.1 GB remains for the OS, dockerd and containerd on a 4 GB VPS. Note this sum includes the OpenAlgo cap that item 1 questions.
- The OOM restart claim is correct: exit 137 plus `unless-stopped` restarts the container; the runbook gives usable inspect commands.
