## Findings
- INFO engine.ts:196-211: all 14 riskSchema keys present. `maxShortOptionQtyPerOrder ?? null` is the only optional key. contractValues is a count (:209). Built field by field, so no env/secret path exists.
- INFO engine.ts:190-192,210: nextNSE uses `this.day.date` (IST date, after `roll()`), filters `>= today` then `.sort()`, so unsorted input is fine. Empty or absent marketHolidays gives `{0, 0, null}`. ISO strings compare lexicographically; the schema's isoDate guarantees the format.
- INFO engine.ts:216-217: remainingOrders and remainingNotional use `this.day.orders` / `this.day.notional`, the same counters as checkOrder (:126,:131), floored at 0. CRYPTO never adds INR notional (reserve :154, recordOrder :177), so CRYPTO orders do not reduce remainingNotional. This matches the engine's semantics.
- INFO engine.ts:197-200: arrays are shallow-copied (strings only) and everything else is a primitive or a new object, so callers cannot mutate engine state. Verified.
- LOW test/tm2_27_risk_status.test.ts (copy test): only allowedExchanges is mutation-checked. symbolAllow, symbolDeny, allowedProducts and `today` are not. Also `process.env.TM2_27_SECRET` is not cleaned up if an assertion fails before the `delete` (use try/finally or afterEach).
- LOW engine.ts:209-210: marketHolidays counts include duplicate dates (config allows duplicates), so `NSE` is the list length, not distinct dates. Acceptable; worth one line in the docs text.
- INFO engine.ts:216: remainingOrders is the daily headroom only. It ignores maxOrdersPerRun, so the AI could still be denied by the per-run cap. maxOrdersPerRun is in limits, so the AI can see it. Consider mentioning this in the api-docs text.
- INFO hand-built RiskConfig (no schema) with non-ISO holiday strings would sort lexicographically. Not reachable through loadConfig.
