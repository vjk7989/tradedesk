## Verified (probed on pandas 2.3.3 and 3.1.1)
- `as_unit("ns").asi8` is correct for naive, UTC and Asia/Kolkata indexes, for both ns and us input; values are identical to the ns epoch (`idx[0].as_unit("ns").value`). On 2.3 it is a no-op, so values are unchanged. On 3.1.1 a bare `asi8` of a us index returns microseconds (1704047400000000), which is the bug this guards against.
- `boundary.as_unit("ns").value` is the UTC epoch for a tz-aware Timestamp, the same basis as a tz-aware index's `asi8`. The localisation at base.py:226-230 still runs first, so naive/aware mixing is unchanged. searchsorted result is 2 for all 6 tz x unit combinations on both pandas versions, side="left" kept.
- Old semantics: `dates.values` on tz-aware is UTC ns and `to_datetime64()` is UTC, so the int compare is equivalent.
- NaT: `asi8` gives the min int64 (-9223372036854775808) after `as_unit`, same as `.values.view("i8")`. Dates reaching here are a unique-merged index with no NaT; no change in behaviour.
- Perf: `as_unit` on a same-unit index returns a copy at worst, O(n) once per call. `_align` pays one extra O(n) copy of the merged calendar; negligible vs the matrix work.
- End to end (probe against the branch source): `_align` with one us loader and one ns loader gives a ns calendar of 6 bars and 6 non-NaN closes for each symbol, naive and UTC, on 2.3.3 and 3.1.1. `evaluation_start_index` returns 2 for ns and us calendars alike.

## Findings
- INFO base.py:299-300: `dates` at :300 is built from ns int64 at :289-294, so `as_unit("ns")` there is already a no-op (as the report says). It is a harmless invariant guard that removes the `.values` use; fine.
- LOW base.py:232-234: a boundary outside the ns range (e.g. `evaluation_start_date="2300-01-01"`) now raises `OutOfBoundsDatetime` from `as_unit("ns")`. On 2.3 the old code silently returned 0 (probe: Timestamp('2300-01-01') unit 's', searchsorted gave 0, which is wrong; the right answer was "after last bar"). Raising is arguably better, but the error is not the friendly "after the last loaded bar" ValueError. Optional: catch and map. Not blocking.

## Orchestrator note (Opus): NaT ordering
The test writer found that with a NaT in the merged calendar, `evaluation_start_index` now returns positions based on int64 order, where NaT is the smallest and sorts first. main used `np.searchsorted(dates.values, …)`, where numpy orders NaT last. `_align` builds `dates` from `np.unique(asi8)`, so a NaT, if a loader ever lets one through, is placed first. main's search therefore ran against an order it didn't match, and its answer was ill-defined. The new behaviour is consistent with how the calendar is actually ordered. The loaders drop NaT index rows (e.g. TM2-17), so this is an edge case. **Accepted**; it is pinned by `test_evaluation_start_index_leading_nat_pinned`.
