## The critical question: does EXECUTE_MAX_CONCURRENT=2 for the whole run affect steps 1-16?
No. Evidence:
- Steps 1-16 are strictly serial (`await step(...)` one at a time, one MCP call each; step 7/11 use a second client but `full` is idle meanwhile). At most 1 execute is in flight, so the cap of 2 is never reached; the busy branch (server.ts:61-64) cannot fire.
- An execute does hold a slot (inFlightExecutes++ before runCode, -- in finally, server.ts:65-70) while awaiting bt-service. That is irrelevant with 1 in flight.
- "backtest service busy" comes from bt-service itself: BT_MAX_CONCURRENCY defaults to 1 (app.py:32), waits BUSY_WAIT_S=30 s, then 429 "busy" (app.py:170-174, 195-199). It is unrelated to the MCP cap (the MCP cap's own text is "busy: too many concurrent executes..."). Smoke never overlaps bt requests, so the flakes are host load (load avg 13-21) pushing a run past 30 s / the timeout, as the developer concluded. Raising/lowering the MCP cap cannot cause them.
- Step 17 does not touch bt-service, and it awaits all 5 results before returning, so no slot is held afterwards (inFlightExecutes returns to 0 before the follow-up), and nothing is left in bt-service. Steps 17/18 are last anyway, so nothing later can be affected.
- Residual bleed only exists from a pre-existing mechanism: if an earlier step hits the 120 s step timeout, step() abandons the promise but the execute (and bt-service run) keeps going. That abandoned execute would still hold 1 of the 2 slots when step 17 starts, so only 1 of 5 could succeed and `>=2` would fail. This is a cascade of an already-failing run, not a new flake.
Recommendation: whole-run cap=2 is acceptable. A separate trade-mcp instance (or restart) for step 17 would be cleaner isolation (and would also make the cap independent of the abandoned-step case), but it is optional, not required.

## Findings
- MEDIUM e2e/smoke.mjs:330 `assert(busy.length >= 1)` is stricter than the task ("2 or more succeed, rest busy"). Legit timing can give 0 busy: the spin loop `await Promise.resolve()` is drained synchronously by runtime.executePendingJobs() (quickjs.ts:225,365) and blocks the host event loop for ~1 s per execute; the other requests queue in the socket. Whether requests 3-5 are admitted while 1-2 are still counted in flight depends on event-loop/HTTP interleaving, so under load (or a different node/SDK version) request 3 can be handled after request 1 finished and then succeed. Then all 5 succeed, which is correct behavior but fails the assert. Suggest dropping the line, or making it robust (e.g. raise the work to 5 s per call, or retry the whole burst once). Note: the guest blocks the event loop, so the 5 calls are not truly parallel; the cap is exercised by admission ordering only. Acceptable for a smoke, but worth a comment.
- LOW e2e/smoke.mjs:322 Same blocking consequence: while a spin runs, trade-mcp cannot answer anything (including /healthz) for ~1 s each, up to ~2-5 s total. Harmless here (steps sequential), but any added concurrent probe in this step would stall.
- LOW e2e/smoke.mjs:156 Cap applies run-wide (see above); document in README that steps 1-16 are serial so cap=2 is inert for them (README currently just says it is set).
- INFO e2e/smoke.mjs:320,327 BUSY string exactly equals server.ts:63 ("busy: too many concurrent executes, retry shortly"); the exec() helper parses the JSON after the PREFIX line so `r.error === BUSY` is exact. `ok + busy === 5` also guards against other errors. `>=2` ok is robust upward (more than 2 may legitimately succeed) and downward except the abandoned-step case above.
- INFO e2e/smoke.mjs:331 Follow-up `return 1+1` on `full` runs after all 5 resolve, so inFlight is 0; correct.
- INFO e2e/smoke.mjs:323-335 Cleanup: the 5 extra clients are closed in `finally` via Promise.all; a failure in connect() itself (Promise.all rejection) would leak the clients already connected until process exit, where cleanup() kills the server anyway. Negligible.
- INFO e2e/smoke.mjs:338 Step 18: matches MEMORY_ERROR "memory limit exceeded" (quickjs.ts:41,67). Uses only plain strings/arrays (no TypedArray/ArrayBuffer/Atomics/WASM), consistent with api-docs.ts:23. ~64 MB cap is hit after ~60k iterations, far below the 5M bound and well within the 60 s execute timeout; recovery via `return 1+1` and /healthz is asserted. Each run gets a fresh wasm module, so recovery is real.
- INFO coord/reports/TM2-53.md Inversion proof is given for one assertion per step (as the task requires). The report is honest about load flakes in steps 9/11/15.
