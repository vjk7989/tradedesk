# Review TM2-36 (PR #64): agent-runner --history [N]

Verdict: APPROVE, no BLOCKER or HIGH. Two MEDIUM and a few LOW items, suitable as follow-ups. I did not run the test suite (reviewed from the diff); the developer reports 955 tests, tsc and build clean.

## Scope and tests
- Only main.ts (arg handling), history.ts (new), test/tm2_36_history.test.ts (new), one README line and the report are touched. The diff adds 166 test lines and deletes none, so existing tests are unedited. PASS.

## Header parsing vs jobs.ts:96-132
- The writer emits `# <name> - <ISO>`, blank line, `- status: ok|error`, `- duration: N ms`, optional `- error: <text>`. history.ts:20-37 matches this exactly.
- The refusal mapping is right: api.ts:61, gemini.ts:121 and openai.ts:65 all write error exactly "refused", and history.ts:31 matches the whole line `- error: refused`. status=error without that line maps to "failed". PASS.

## No body or error text printed
- Printed fields are job name (regex-constrained to [A-Za-z0-9_-]+ by parseJobs), file stem (regex-validated by FILE_RE), a status from a closed set, a numeric duration and the path. Body and error text are never kept or printed. PASS.
- LOW, main.ts:~120 / history.ts:79: the path (outputDir) is printed unredacted. TM2-30 dry-run pipes every line through redactor(). outputDir is operator-chosen and a secret in it is unlikely, but redactor() is cheap, so reuse it for consistency and defense in depth. Not required.

## Every --history* form (main.ts, new block)
- `--history`, `--history N`, `--history=N` and `--history 5 --jobs x` are handled correctly.
- `--history=`: Number("")=0 and the regex fails, so it exits with the "positive integer" error. PASS.
- `--history5` and `--history-x`: rejected with "unknown option" and exit 1. PASS.
- `--history --check` and similar combinations are rejected. `--history --foo`: a starts with "--", so N=20.
- The whole block always ends in `return exit(...)`, so nothing reaches the scheduler. PASS.
- LOW, main.ts: findIndex takes only the first `--history*` token. `--history --history5` or `--history=5 --history5` silently ignores the second token. It is harmless, since nothing reaches the scheduler, but a strict check would be to scan all tokens.

## Conflicts
- The flags --once, --check, --next and --dry-run are covered in both bare and `=` forms. PASS.
- The test covers `--history <flag>` order only.

## N validation vs --next
- Same structure and wording. Number(a)>max is checked first, then the regex and <1 check, which gives the same oddities as --next ("1e2" and "-5" are rejected, "007" is accepted). Max is 200 per brief. PASS.

## Ordering
- Sort is header time desc, then -n numeric desc, then path. This is correct across jobs and for same-day -n files. Dedup of identical dirs is fine. PASS.

## Path traversal and symlinks
- Job names are regex-safe, and only `<outputDir>/<name>` is listed. There is no traversal beyond what the operator's outputDir implies. FILE_RE filters filenames.
- LOW, history.ts:59-61: readFileSync follows symlinks, and a `2026-01-01.md` that is a symlink or FIFO/device (for example /dev/zero) is read in full: unbounded memory, or a hang on a FIFO. Content is never printed, but this is a DoS and an info-existence side channel. The threat model is local write access to outputDir, so low severity. Fix: lstat/isFile() check, or open and read a bounded header.

## Large outputDirs
- MEDIUM, history.ts:59-61: every matching report in every job dir is read in full (readFileSync, then split on all lines) just to parse about 4 header lines. Reports contain full prompt and result bodies, and the runner can run for years, so time is O(total bytes) and the peak is one whole file plus its line array. Rows are small, so retained memory is O(file count) and acceptable. Fix: read only the first 4 KiB (open, read, close), and/or pre-sort candidates by filename date and stop once N valid rows are found. The latter needs care because the header time and the IST filename date can differ, so over-read by a day.
- MEDIUM (same spot): `rows` holds all reports before slice(0,n), which is bounded by file count and fine on its own. Combined with the full-file reads above, the practical cost is dominated by IO.

## Header-injection (LOW, history.ts:27-34)
- The loop uses last-match-wins and scans lines after the `- error:` line. The error text is arbitrary (CLI stderr, which can be multi-line), so a line within it such as `- status: ok` or `- duration: 1 ms` (before the first blank line) overrides the real value. Use first-match-wins and stop scanning at the first `- error:` line, or only accept status and duration before it. The writer always emits status and duration before error, so this is a safe fix.

## INFO
- Reports with an unknown status or an unreadable file are counted as skipped. A missing job dir is silently ignored, which matches the brief.
- The test spies on spawn, execFile and fetch, and asserts runTask and runScheduler are not called. Good coverage of "runs nothing".

## Fix plan — round 1 (Opus)
The edge tests (head `eaa6e2a`) leave 3 tests red on purpose, matching the review's MEDIUM and LOW findings. Fix in `agent-runner/src/history.ts`, plus `main.ts` only for the redactor wiring. Do not edit tests.

1. **HIGH: status spoofing.**
   - `parseReportHeader` must use **first-match-wins** for `- status:`, `- duration:` and the timestamp.
   - It must **stop parsing at the first `- error:` line**: the error text written by cli.ts:276 can contain `- status: ok`.
   - A failed run must never be displayed as ok.
2. **Bounded read.**
   - Read at most the first 4096 bytes of each report (`openSync`/`readSync`/`closeSync`), never `readFileSync` of the whole file.
   - A header that doesn't fit in 4 KiB is skipped and counted.
3. **Non-regular files.**
   - Before reading, `lstatSync` the entry and only read regular files. Symlinks, FIFOs and devices are skipped and counted as unreadable.
   - This changes the documented behaviour that "a symlink is followed"; the test writer updates that test (an AC change).
4. **Redaction.** Pass the job name and path through the same `redactor()` that `--dry-run` uses in main.ts, with the same short-secret rule: if any set secret is shorter than 4 characters, print `[withheld: a referenced secret is shorter than 4 characters]` for the name and path columns. Reuse it; don't re-implement it.
5. **Verify** with `npx vitest run && npx tsc --noEmit && npm run build`. Expect the 3 bug tests to pass; list anything else that fails.
