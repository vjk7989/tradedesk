# TM2-37 review (PR #72): de-flake sandbox "50 sequential runs"

Verdict: APPROVE WITH COMMENTS. No BLOCKER or HIGH. Two MEDIUM findings (slow-leak sensitivity, median-ratio under non-stationary load) are cheap to fix and I recommend doing so before merge.

## Scope and intent
- Diff touches only `trade-mcp/test/sandbox.edge.test.ts` (two imports, lines 2-3, plus the one test at 379-418) and `coord/reports/TM2-37.md`. No `src/`. Scope OK.
- Intent kept: 50 timed runs, each asserted `ok: true, result: [1, i]` (401), memory (410-411), handles (413), and the median(last 10) <= 2x median(first 10) degradation check (415-417). The 5 warm-up runs (390) are also asserted.
- Timeout 12 s (418) is justified: worst loaded 50-run loop 3.845 s x 3 = 11.5 s, matching the brief's ~3x rule. Rewritten test measured at most 2.86 s loaded, so there is a 4x margin.

## Findings

### MEDIUM-1 `sandbox.edge.test.ts:410-411` memory limits let slow leaks pass
- Only RSS (+64 MB) and external (+32 MB) are checked; `heapUsed` is not. A 1 MB/run leak (50 MB total) of JS-heap objects (retained results, closures, guest handles held in Node) is under both limits and passes. A 1 MB/run leak in native/WASM memory shows as external (+50 MB > 32 MB) and would be caught, but 0.5 MB/run (25 MB) would not.
- The "leak" proof (~798 MB external, ~16 MB/run) only shows gross leaks are caught. No slow-leak proof was run.
- The reported healthy values leave a lot of room: RSS growth <= 12 MB, external <= 0 MB.
- Recommend: external < 8 MB (observed <= 0), RSS < 32 MB, and add `heapUsed` growth < ~10 MB after gc. Re-run the 20 loaded runs to confirm no false failures, and prove once that a 1 MB/run retained buffer now fails. The 64/32 MB values were copied from the 200-run O-9 test; with a 4x shorter loop the same absolute limit is 4x less sensitive per run.

### MEDIUM-2 `sandbox.edge.test.ts:415-417` 2x median ratio can false-fail on a load step
- With 10-run medians, a random p99 spike is not a risk (a single outlier cannot move the median; it takes >= 5 slow runs in a window). Measured worst ratio 1.16 over 30 loaded runs supports this.
- The real risk is non-stationary load. Alone p50 is 8 ms, loaded p50 is 28 ms (3.5x). If the other suites enter a heavy phase part-way through the 0.4-2.8 s test, first10 is quiet and last10 is loaded, and the ratio exceeds 2 with no regression. The 30 diagnostic runs were steady-state load, so this case was likely not sampled. Likelihood is low-moderate on CI with parallel workers, and it would be a hard-to-diagnose flake, which is what this task is meant to remove.
- Recommend a small absolute floor: `last <= Math.max(2 * first, first + 50)`. Slowdown B2 (121 ms vs 35 ms) still fails with it, and B (70.7 vs 33.9) would pass, so choose the floor deliberately, e.g. 25-30 ms, or keep B as the sensitivity target.

### LOW-1 `sandbox.edge.test.ts:413` handle slack of +2
- The check is reliable as written: `process.getActiveResourcesInfo()` is a snapshot of the main thread's resources, the vitest 12 s test timer is present in both baseline and end, the `sleep(20)` timer has fired before the end sample (405 is awaited), and the tests in a file run sequentially. A per-run leak of 1 handle gives +50 and fails. A leak of only 1-2 handles in total is allowed. It is also an unordered count, not a type check, so a swap (a Timeout replaced by a different resource) passes. Fine as a smoke check; optionally compare per-type counts.

### LOW-2 `sandbox.edge.test.ts:380-381` GC forcing is safe, with a caveat
- `v8.setFlagsFromString("--expose-gc")` plus `runInNewContext("gc")` does not add `globalThis.gc` to the test's realm (only new contexts get it), and it is already used by `o9_sandbox_hardening.edge.test.ts:66` and `o9_sandbox_hardening.test.ts:240`. The flag is process/worker-wide and persists, but it only affects new vm contexts, not other tests' behaviour. This test is the last in the file, so no later test in the file is affected anyway. The imports are test-scoped (`node:v8`, `node:vm`). No action needed. Note that `gc()` is a full synchronous GC; it is called twice on 404-406, negligible cost.

### LOW-3 `sandbox.edge.test.ts:418` timeout headroom on smaller CI
- The numbers come from an 8 vCPU box. On a 2 vCPU runner the same two-suite load would be proportionally worse. 12 s still has about 4x margin over the observed test time (2.86 s), so only a note.

- 20/20 loaded passes used `-t "50 sequential"`, so the other tests in the file (which run before this one in a normal run) were not part of that state. The full run in the report also passed (1.46 s). Acceptable.
