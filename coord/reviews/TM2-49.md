# Review TM2-49 (PR #83): revoke-all and DATA_DIR lock cross-platform (Windows), plus source fixes

Reviewer: independent (Opus). Static review of origin/tm2/TM2-49 against origin/main. I did not re-run the suite and have no Windows machine. I verified the symlink behaviour of `argv[1]` vs `import.meta.url` with a small node experiment.

## Verdict: APPROVE. No blocker or HIGH. Linux behaviour is unchanged. Three MEDIUM/LOW items are recommended as follow-ups, not gating.

## Scope (pass)
Source: datadir-lock.ts (+3), provider.ts (+10/-1), revoke-cli.ts (+6/-1). Tests: the four brief files plus new tm2_49_cross_platform.test.ts, plus the report. The brief allowed source only for real Windows bugs and the report says which (S1 real bug, S2 pid reuse, S3 optional); S3 is the weakest justified but is tiny and safe. No secrets (the only grep hits are fake test strings: `OAUTH_PASSWORD_HASH: ""`, `passwordHash: "x"`). No unrelated changes.

## S1 revoke-cli main guard (revoke-cli.ts:83-87)
- Fixes the real bug: `new URL(...).pathname` gave `/C:/...` on Windows and `%20` on any OS. `fileURLToPath` is correct.
- No false positive. Importers of revoke-cli: only tests (tm2_35 x2, tm2_46 x2, tm2_49 text) via `import { run }`; index.ts does not import it (it imports only datadir-lock). Under vitest/server `argv[1]` is the vitest or server entry, never revoke-cli, so the guard is false. The guard cannot fire on import.
- Relative `argv[1]`: `path.resolve` against cwd, correct. Missing `argv[1]` (node -e, REPL): guard false, no run (correct).
- Case-insensitive on win32 only: fine. Not applied on darwin (case-insensitive default FS) but argv[1] and import.meta.url share the user's spelling there; ignore.

### MEDIUM-1 Symlinked invocation is still a silent exit 0 no-op (revoke-cli.ts:83-87)
Node keeps `argv[1]` as the path the user typed (symlink not resolved) but `import.meta.url` is the realpath. I confirmed: `node link/a.mjs` prints different strings for the two; `node real/a.mjs` prints equal ones. So `node /some/symlink/dist/src/oauth/revoke-cli.js --force` runs nothing, prints nothing and exits 0, which on a security command reads as "revoked". This is the same failure class the PR fixes, only for symlinks (pre-existing, not a regression; the documented compose command uses a real relative path so it is not hit in production). Fix: compare `realpathSync(argv[1])` (try/catch fallback to the resolved path) with `realpathSync(fileURLToPath(import.meta.url))`. Cheap and removes the whole class. Also worth failing loud: if the file is run directly but the guard is false there is no signal; consider a package.json-level check or test.

## S2 datadir-lock.ts classify/procStart (datadir-lock.ts:30-32, 81-82)
- Linux byte-identical: `procStart` gains a `platform !== "linux"` early return (true on Linux, so the /proc path is unchanged) and the new branch requires `process.platform === "win32"`. Verified from the diff; the tm2_49 "linux unchanged" test covers it.
- A live Windows server is not judged stale in normal running: heartbeat is 5 s (HEARTBEAT_MS) vs the 15 s window, a 3x margin; `utimesSync` works on NTFS. `ageMs` passed by checkLock/acquireLock is the real mtime age; unknown age (Infinity) stays live (fail closed).
- Event-loop block >= 15 s on Windows: a same-host lock with a live pid is judged stale, a second instance replaces it (two servers; the old heartbeat then stops because pid no longer matches) and a CLI would proceed against a running server. This is the same rule as the existing cross-host case, so it is a consistent, accepted trade-off. The report states it.
- Windows has no Linux-style safety net here (see LOW-1): the replace is safe only while the old server is merely stalled; EADDRINUSE on the same port is the backstop for starters.
- darwin / other: `procStart` is now explicitly undefined; before, the /proc read failed and returned undefined, so behaviour is unchanged. Result: liveness = pid alive only, no pid-reuse detection, no heartbeat rule. It fails closed (a reused pid blocks startup until the lock is deleted by hand), consistent with pre-PR behaviour.

### MEDIUM-2 Windows sleep/resume or pause can produce a false "stale" (datadir-lock.ts:82)
A laptop suspend, debugger pause or VM freeze longer than 15 s makes the heartbeat age exceed the window while the server is alive; during the first <= 5 s after resume, `oauth:revoke-all` or a second start sees "stale" and proceeds. The CLI case matters: the server then re-persists its in-memory tokens and undoes the revoke (the TM2-35 HIGH-1 failure). Window is narrow and Windows is a dev environment, not production (Linux container), so not gating. Mitigation if wanted: on win32 also require the age check to hold twice a few hundred ms apart, or have the CLI warn "stale on Windows: confirm the server is stopped" on win32 stale-with-live-pid.

### LOW-1 darwin has no pid-reuse recovery (datadir-lock.ts:81-82)
The comment and rule are win32-only; darwin (and any non-linux) can wedge on a reused pid forever. Fail closed and out of scope for production; consider `platform !== "linux"` instead of `=== "win32"` for the heartbeat rule, since the reasoning (no spawn-free start time) is identical. Also the doc comment at datadir-lock.ts:24-25 and the LockHeldError text ("After a crash, wait up to 15s") are not accurate for these cases.

## S3 persist retry (provider.ts:135-145)
Pass. Bounded: 3 retries (4 attempts), 50 ms sleep via `Atomics.wait` (synchronous, consistent with the surrounding sync persist and datadir-lock's own sleepMs; worst case 150 ms blocking on Windows only), only EPERM/EBUSY, everything else thrown on the first attempt. The tmp file is written with mode 0o600 before the loop and the rename and chmod are unchanged, so atomicity and file mode are unchanged. On final failure the original store is untouched (tmp left behind, same as before). On Linux EPERM/EBUSY on rename essentially never occurs, so no behavioural change.

### INFO-1 A failed persist leaves `oauth.json.tmp` (pre-existing)
Same as before the PR; contains the token store at 0o600. Not new.

## Tests
- Windows skips (about 14): each has an explicit comment with a reason, and each is genuinely POSIX-only: chmod 0o555/0o000 dir/file semantics, symlink privilege (EPERM), /proc start time, and SIGTERM/SIGINT via ChildProcess.kill on Windows terminating the child outright. Linux skip conditions are only extended (`IS_ROOT || IS_WIN`), so they evaluate identically on Linux. The conditional case-list entry is spread-included on Linux. Linux 2370 -> 2383 passed, 4 -> 5 skipped: +13 new tests and +1 skip (the win32-only `it.runIf` test), as expected and acceptable under the brief.
- Test infra changes (sleep -> node child, sh -> node, tsx shim -> `node --import tsx`, procStartIfAny) are sound and equivalent on Linux.
- tm2_49_cross_platform.test.ts is meaningful: S1 spawns the real CLI from a copied tree with a spaced path and asserts store mutation (it would catch the silent no-op); S2 stubs `process.platform` at call time (restored in `finally`) and covers fresh, window-1, window, unknown, dead, own pid, procStart ignored, acquire/replace, linux/darwin unchanged, foreign host; S3 mocks renameSync only for `oauth.json` and checks attempt counts. The report's mutation run (9 of 13 fail on the old source; the 4 that pass assert already-correct behaviour) is credible.

### LOW-2 Windows loses real-server lock coverage
The two real-process lock tests are skipped on Windows entirely (they need graceful SIGTERM), so the acquire/heartbeat/release path in index.ts has only the platform-stubbed unit coverage there. Acceptable, but an owner Windows run is the only real check of S1/S2/heartbeat on NTFS; keep that as the acceptance gate (brief says the owner re-runs on Windows).

### LOW-3 S1 test needs symlinked node_modules (tm2_49 test:69)
`symlinkSync(..., "junction")` works on Windows for directories without admin, but if node_modules is absent in a fresh worktree beforeAll throws a generic ENOENT. Cosmetic.
