# TM2-17 review (independent)

Verdict: APPROVE (no blockers). One MEDIUM edge-case behaviour change, noted below.

Scope: the diff touches only the ISO branch at india_broker_loader.py:115 (one line plus a comment), the new test file and coord/reports/TM2-17.md. No warning filter was added in source. The existing tests are unedited. No secrets. uv.lock pins pandas 2.3.3, so `format="ISO8601"` is supported. I ran old and new parse side by side on 2.3.3.

## Findings

- MEDIUM, india_broker_loader.py:115. A column that starts with a naive string and has an offset string later (for example `["2024-03-01T09:15:00","2024-03-01T09:16:00+05:30"]`) behaves differently. The old inferred parse returned NaT for the offset row, so the row was silently dropped. The new parse returns an object column, and `tz_localize(None)` at line 117 raises `ValueError: Tz-aware datetime.datetime cannot be converted...`. The old behaviour was already wrong because it dropped data. The new one can crash the loader for that bar set. A single broker feed is unlikely to mix forms like this, so this is not a blocker. Suggest a follow-up that parses with `utc=True`, or accepts this and documents it. Also note the data-quality side: mixed offsets (`+05:30` and `Z`) already gave an object column and a FutureWarning on both paths, so that case is unchanged and still warns.
- LOW, india_broker_loader.py:115. Mixed `T`/space separators, date-only mixed with datetime, and compact `20240301T091500` forms were inferred from the first element in the old path, so the other rows became NaT and were dropped. ISO8601 parses every row. This is a value change, but only on malformed or mixed input, and in the better direction. A uniform column, which is every case the brief lists, is identical.
- LOW, india_broker_loader.py:115. Non-ISO strings are now NaT where the old path sometimes inferred them. Example: `["01/03/2024 09:15", ...]` gave 2024-01-03 (month-first, a likely mis-parse) in the old path and NaT now. The comments and docstring say the broker sends ISO or epoch, so this is acceptable.
- LOW, coord/reports/TM2-17.md. This file is outside the brief's "Files you may touch" list. It matches the usual report convention, so it is harmless. Confirm that it is expected.
- LOW, bt-service/tests/test_tm2_17_broker_time.py. The tests only cover uniform columns. They do not pin the mixed-column behaviours above, and there is no test that the numeric (epoch) branch is untouched. The expected value comes from a legacy parse inside the test, which is fine, but the "legacy" run suppresses warnings only, so it does confirm value identity. Epoch-like strings (`"1709284500"`) never reach this branch because `pd.to_numeric` succeeds first at line 109, so they are unaffected.
- INFO. For offset strings (`+05:30`, `Z`), `tz_localize(None)` keeps the wall-clock value without converting to IST. Both paths do the same, so this is not a regression. It is worth knowing if a broker ever sends UTC `Z`.
- INFO. Bad strings still become NaT, and the test for that passes. Mixed-row bad input (`["not-a-date","2024-02-29T10:00:00"]`) is the same in both paths and no longer warns.
- INFO. I did not re-run the full suite. The developer's counts (1866 passed, warnings 404 to 403) are plausible but unverified by me. My empirical checks covered 16 string shapes.
