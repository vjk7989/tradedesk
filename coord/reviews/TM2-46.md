# Review TM2-46 (PR #76): DATA_DIR lock for oauth:revoke-all

Reviewer: independent (Opus). Static review of origin/tm2/TM2-46 against origin/main. I did not re-run the suite. CI was still in progress when I looked.

## Verdict: APPROVE (no blocker; merge-safe for production). Two MEDIUM race/robustness items and a few LOW/INFO items are recommended as follow-ups, not gating.

The lock cannot stop trade-mcp from starting under the shipped compose file. Its real protective value is narrower than the PR title suggests (see MEDIUM-3), and the report says so honestly.

## Scope (pass)
- Files: datadir-lock.ts (new), index.ts (+3 lines), revoke-cli.ts, tm2_46 test (new), coord/reports/TM2-46.md. All within the brief's list.
- index.ts diff is the import (line 9), `acquireLock` + `process.on("exit", releaseLock)` (32-33). Nothing else touched; no sandbox code.
- No existing test edited (the diff only adds one new test file). The runbook is not touched (see LOW-1).

## Locking
- `wx` exclusive create (datadir-lock.ts:82) is race-free for the create itself.
- Stale replace is NOT fully race-free: see MEDIUM-1 and MEDIUM-2. The report's claim "two simultaneous starters on a stale lock end with one winner" is overstated.

## Shutdown (pass)
- SIGINT/SIGTERM -> `stop()` -> `http.close(() => process.exit(0))` (index.ts:37-42, unchanged) -> `exit` event -> `releaseLock`. Uncaught exceptions and `process.exit(1)` also fire `exit`. SIGKILL leaves the lock, which the next start treats as stale/foreign and replaces.
- Release only unlinks if pid, startedAt and hostname still match ours (datadir-lock.ts:86-87); tested. Graceful-shutdown behaviour is otherwise unchanged. The `exit` handler is registered synchronously right after acquisition, so there is no window where we hold a lock without a release hook.
- Ordering: acquired after config/risk/deps construction and before `listen`, so a refused start never binds the port.

## Deployment safety (critical): cannot prevent start in production
- (a) `docker compose restart` keeps the same container: same hostname, server is pid 1 again, lock pid 1 equals own pid -> "stale", replaced (datadir-lock.ts:55). `up -d` recreation or `compose run`: new container id means new hostname -> "foreign", replaced (:54). Old container is stopped before the new one starts. OK.
- (b) Crash and `restart: unless-stopped`: same container, pid 1 == pid 1 -> stale, replaced. SIGKILL after the 10s stop grace: lock left, replaced next start. OK. A refusal (exit 1) could only happen with same hostname and a different live pid, which cannot occur with node as the container's pid 1.
- (c) compose.yml has no `hostname:` (checked), so hostnames are per-container. If an operator ever sets a fixed `hostname:`, the self-pid rule means a lock from another container's pid 1 reads as "stale", never "live", so starts are never blocked (fail-open), but the CLI would then print "no live trade-mcp process" misleadingly (LOW-2).
- (d) Read-only / full DATA_DIR: `mkdirSync`/`openSync`/`writeSync` throw EROFS/EACCES/ENOSPC out of `acquireLock` (:72, :82-83), caught only by main's `fatal:` handler, exit 1, then a restart loop. Before this PR, start succeeded and failed later on first audit/risk-state write. So this is a behaviour change, see MEDIUM-4. My recommendation: EROFS/EACCES failing at start is acceptable (the server cannot write audit.jsonl or risk-state.json anyway, and failing loud is better than failing at the first trade), but the message should name the lock. ENOSPC is the one case I would fail open (warn, run without lock), because a full disk should not take the server, including the kill-switch host, offline for an advisory file.
- (e) stdio: returns at index.ts:30 before the lock. Right: stdio has no oauth store or HTTP listener and is not the revoke race; two stdio processes are independent. Note stdio shares risk-state/audit files with an HTTP instance but this is out of scope.

## revoke-cli trade-off
- Live lock -> exit 4 even with --force; checked before any store read. Foreign -> warning and proceed; stale/corrupt -> note and proceed. For the documented `stop -> compose run --rm --no-deps -> start` flow this is the only workable choice: the stopped container's lock is foreign (or removed on clean exit) and must not block. The cost: in the documented flow the lock gives NO protection against the one mistake it was meant to catch (forgetting `stop`). See MEDIUM-3 for a cheap improvement.
- Exit 4 is documented in the CLI and report but not in the runbook (LOW-1).

## Honesty (pass)
The report's "Honest limits" section is accurate and candid: same-namespace only, foreign lock proceeds with a warning, hostname override, advisory only, Linux-only start-time check. Only the race claim is overstated (MEDIUM-1/2).

## Smoke
The lock is sync fs work in index.ts startup only; it is not on any request, bt or walkForward path (bt-service is a separate container, and the CLI is not involved). It cannot plausibly cause walkForward-busy or timeout failures in smoke steps 9/11/15; load average ~22 explains them. Ask for a re-run on a quiet machine before relying on it, and make sure no stale trade-mcp from an earlier smoke run is holding the same DATA_DIR (a live same-host lock now makes a second start refuse, by design).

## Findings

### MEDIUM-1 Stale-replace can unlink someone else's fresh lock (datadir-lock.ts:92-102)
B reads a stale lock, A (also seeing it stale) unlinks and creates its own, then B unlinks by path (`:102`) and deletes A's live lock, then B creates. Both believe they hold it. Narrow window, and a second listener on the same port/host would fail with EADDRINUSE as a backstop, but it is exactly the TOCTOU the brief asked about. Fix: replace by atomic rename of the observed file to a unique name and verify its content equals what was classified, or take a short `wx` guard file (e.g. `trade-mcp.lock.replace`) around replacement.

### MEDIUM-2 Non-atomic lock write lets a reader see an empty file as "corrupt" and replace it (datadir-lock.ts:82-83, 53, 99-102)
Between `openSync("wx")` and `writeSync` the file is empty; a concurrent starter reads it as "corrupt", unlinks it and creates its own. The first process then writes into an orphaned inode. Same effect as MEDIUM-1. Also a failed `writeSync` (ENOSPC) leaves an empty lock. Fix: write a temp file then `linkSync` it to the lock name (atomic and exclusive), or treat a very young corrupt lock as live.

### MEDIUM-3 No cross-container protection in the documented flow (revoke-cli.ts:38-40; report "Honest limits")
Forgetting `docker compose stop` leaves a live server in another container, the lock is "foreign", and the CLI proceeds with only a warning, which is the exact failure TM2-35 HIGH-1 described. The limit is honestly stated and acceptable for this task, but a cheap follow-up closes it: in the foreign case, probe `http://trade-mcp:8787/healthz` (reachable from a `compose run` container on the `internal` network) and exit 4 if it answers; or have the server touch a heartbeat in the lock and treat a recent mtime as live.

### MEDIUM-4 New start failure modes for unwritable/full DATA_DIR (datadir-lock.ts:72, 82-83; index.ts:32)
See (d). Not a blocker. Wrap non-EEXIST errors so the message says "cannot create trade-mcp.lock in DATA_DIR: <code>"; consider fail-open on ENOSPC.

### LOW-1 Runbook not updated (docs/vps-runbook.md section 13, exit-code bullet)
It still lists exit codes 0-3; 4 and the lock behaviour are missing. The brief's file list did not allow docs, so ask for a small docs follow-up.

### LOW-2 Same-hostname, same-pid case reports "no live trade-mcp process" (revoke-cli.ts:41-42, datadir-lock.ts:55)
With a fixed `hostname:`, a `compose run` CLI (pid 1) sees a live server's lock (pid 1) as "stale". Result is still proceed, but the note is misleading. Only matters if someone sets `hostname:`.

### LOW-3 Test coverage gaps (tm2_46_datadir_lock.test.ts)
No test for concurrent acquire (MEDIUM-1/2), unwritable DATA_DIR, or the index.ts wiring (signal -> lock removed). Library-level only; the shutdown path is verified by reading, not by test.

### INFO-1 `process.kill(pid,0)` EPERM counted as alive (datadir-lock.ts:35): correct, conservative.
### INFO-2 /proc start-time parsing (field 22 = index 19 after the comm paren) is right (:30).
### INFO-3 revoke-cli.ts lines 61-77 are mis-indented (pre-existing, not from this diff); cosmetic.
### INFO-4 The two failing full-suite tests (O-8 sandbox, market-holidays perf) are timing tests unrelated to this diff.
