# O-6 review

## Code review (Sonnet)

Verdict: changes-needed (minor).

The new assertions are negative-only, so they are weaker than /memory/i. Any non-timeout failure passes them.
- sandbox.test.ts:58-63 and sandbox.edge.test.ts:298-306: a ReferenceError, "stack overflow" (quickjs.ts:67) or any other thrown error passes, and so does a broken cap that lets a later non-memory error surface. Syntax errors return early as "syntax error: ..." (quickjs.ts:58), which also passes.
- If the cap stops working, the infinite loop runs until the interrupt handler (quickjs.ts:68) or the timer (:177) fires, and fail() reports timeout. That is caught, but only after 20s. A finite allocator would pass silently.
- edge test 3 (:318-326) is the only positive control, but it allocates 1MB under a 4MB cap, so it does not prove the cap is what stopped the loop.

Minimal fix, still deterministic: add a control that runs the same finite allocation, for example 16 x 1MB retained, twice. With memoryBytes 64MB it must give ok:true. With 4MB it must give ok:false and error not matching /timeout|syntax|ReferenceError|stack/. Also assert error matches /memory/i OR /InternalError/.

## Security review (Sonnet), O-8

Verdict: changes-needed (no blockers found, 2 mediums).

1. Removed globals (quickjs.ts:83-85) - OK. Deleted right after newContext, before user code; the deletion runs in the host-controlled context, so user code cannot capture a reference first. LOW: `delete` is sloppy and silent on non-configurable props, and nothing verifies the result. Add a post-check (`typeof X === "undefined"` for each) and fail closed. Spec asks for this to be provable.
2. Binding caps (:157-182) - MEDIUM: vm.dump(argHandle) and JSON.stringify run BEFORE the 1 MB check (:157,160). The host copy is bounded by the guest heap (memoryBytes) not by 500 MB, but transient host cost is ~3x memoryBytes per call, and calls run synchronously. Measure in-guest instead (JSON.stringify inside the VM, check .length, then dump). In-flight and pendingBytes accounting is correct: rejected-at-cap calls take no slot, and the decrement is in .finally (:202-206), so it covers throw, reject and settle. pendingBytes <= memoryBytes is enforced (:174). Infinity is handled (:162).
3. Heap ceiling (:86-95) - MEDIUM: ceiling is memoryBytes+16 MB, not the brief's +32 MB (deviation, stricter; fine if intended, but document it). The interrupt handler only fires on guest bytecode, so a single native op (repeat, Array fill) or a guest parked on `await binding()` is not checked until it ends or the timeout. The post-run check (:94) catches the peak, so the host survives, but it reports memory error only after the work was done. Fire-and-forget bindings: the run result is still replaced by the memory error, which is correct.
4. Disposal - LOW: finally (:98-102) always disposes vm and runtime, including on error and timeout. But `jsonParse` (:105) is never disposed, which is a pre-existing handle leak. vm.dispose() can then throw and is swallowed (:263-274), and the context and runtime may remain live. Dispose jsonParse in finally. The WASM module has no dispose and is freed by GC, so confirm with a loop test that RSS is flat.
5. Return values (:186-196) - MEDIUM: binding results are not size-capped. JSON.stringify(value) of a huge host result is held in the host and copied into the guest. Only the guest memory limit stops it (the throw is caught at :191-193). Add a result cap, e.g. 1 MB or memoryBytes, checked on the stringified length before newString.
