# TM-13 review

## Code review (Sonnet)

Verdict: approve (minor suggestions, none blocking).

Verified: codes/pending keyed by sha256, no plaintext rid/code/IP/verifier/password in oauth.json (test covers it); persist() is 0600 + tmp + rename; load prunes expired codes/pending/failures; corrupt file starts empty, static token unaffected; limiter window semantics (15 min, 5 fails) unchanged; stored PKCE value is the challenge only. Single-use: codes.delete + persist() run synchronously before tokens are issued (provider.ts exchangeAuthorizationCode); Node is single-threaded and the sync write leaves no double-spend window. If persist throws, the code is already gone in memory, so it fails closed. In-process maps are the source of truth and every write rewrites the whole file synchronously, so no map/file race.

Findings:
1. low, login.ts hashIp: unsalted sha256 of an IPv4 address is reversible by brute force (about 4e9 inputs). The IPs are not plaintext but are effectively recoverable if the file leaks. Fix: HMAC with a random per-install secret stored in oauth.json, or accept and document.
2. low, provider.ts exchangeAuthorizationCode: persist() runs even for unknown codes, and authorize() persists per request. Unauthenticated /token and /authorize calls therefore each cause a full synchronous file rewrite. Fix: persist in exchange only if rec existed; consider a cap on pending size.
3. nit: no test for a failed persist (read-only dir) during exchange.

Write frequency per login is acceptable.
