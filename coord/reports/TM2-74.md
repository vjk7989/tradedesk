# TM2-74 report: agent-runner interval schedules (everyMinutes)

## Design
- `Schedule` gains optional `everyMinutes` and `between`; `time` becomes optional. Exactly one of `time`/`everyMinutes` (parse error naming the job otherwise).
- `nextRun` dispatches to `nextIntervalRun` for interval schedules; the `time` path is untouched.
- Files changed: `agent-runner/src/jobs.ts`, `src/scheduler.ts`, `src/main.ts` (only the `schedule:` line of `--dry-run`, which printed `schedule.time`), README. Run loop = `runScheduler` in scheduler.ts (main.ts only wires it).
- Tests not edited. jobs.gemini-paper.example.json NOT changed (the brief does not ask for it, and tm2_73_gemini_paper_job.test.ts asserts a `time` schedule). README text for the cron workaround now says it is the pre-TM2-74 alternative.

## Edge-case decisions
- everyMinutes: integer 5..1440; 0, 4, 1441, 7.5 rejected. 1440 gives one slot per day at 00:00.
- Grid is local minute-of-day k*N, restarting each local day; if N does not divide 1440 the last gap is shorter (N=7: 23:55 then 00:00).
- `days` filters by local weekday of the slot.
- `between`: both ends inclusive, start < end required (no overnight wrap, start==end rejected), HH:MM only. Does not re-anchor the grid (45 min in 09:15-15:30 gives 09:45...). Rejected with `time`.
- IST fixed +05:30, UTC; no DST, so no DST handling (confirmed: Mar/Oct DST-date start instants are in the identity run, results identical).
- Overlap: the scheduler is a single sequential loop, so runs can never actually stack. After a run finishes, interval slots that fell in (due, finish] are logged per slot as `job <name>: slot <ISO> skipped (previous run still active)`, then the next due is the first grid slot after the finish time (absolute grid, so later slots do not shift). Only interval jobs log this; `time` jobs behave exactly as before. Note a slot delayed only by ANOTHER job running is run late, not skipped (existing behaviour).

## Review
Reviewer verdict: **CHANGES REQUESTED** (one blocking finding, 1; the rest are non-blocking).

Verified: `npm ci`, `npx vitest run` (32 files, 1061 passed), `npx tsc --noEmit`, `npm run build` all clean. No stray processes; scratch worktree removed.

1. **BLOCKING, agent-runner/src/jobs.ts:65-72 (parse) / scheduler.ts:41 (`throw "no next run"`).** A `between` window that contains no grid slot is accepted by parse and `--check`, then the runner dies. Repro: `{"days":["Mon"],"everyMinutes":60,"between":["09:10","09:50"],"tz":"UTC"}`: `--check` prints the table and passes; `--next 2` prints `fatal: no next run`; `runScheduler` calls `nextRun` at startup, so the whole process (all jobs) crashes. On main no accepted schedule could throw this. Fix: in parse, reject when `ceil(lo/n)*n > hi` with a message naming the job (e.g. "schedule.between contains no slot for everyMinutes N").
2. Non-blocking, jobs.ts:50-72. Validation otherwise tight. Rejected: "30" (string), -5, NaN, null, 0/4/1441/7.5 (per dev), `between` of `24:00`, `9:5`, equal ends, reversed (overnight), 3 elements, null, a string, `between` with `time`, both/neither of `time`/`everyMinutes` (all name the job). Accepted: 5, 1440, `5.0` (JS integer, fine). Unknown keys inside `schedule` (e.g. `foo`) are silently dropped. That is also pre-existing behaviour for `time` jobs, so only a hardening suggestion (a typo like `everyMinute` with no `time` gives the "exactly one of" error, so the common typo is caught).
3. Non-blocking, next-run math (all as expected, expected == actual):
   - N=7 UTC from 2026-11-28T23:40Z: 23:41, 23:48, 23:55, then 00:00 (5-min last gap), 00:07. Correct (grid anchored at 00:00, restarts each day).
   - N=7 IST from 18:20Z (23:50 IST): 18:25Z (23:55 IST), 18:30Z (00:00 IST), 18:37Z (00:07 IST). Correct (IST boundary).
   - N=1440 IST: one slot per day at 18:30Z, strictly-after at an exact slot moves to the next day. Correct.
   - 30 min UTC Sat/Sun from Fri 23:45Z: Sat 00:00Z, 00:30Z, 01:00Z. Correct. Sat only from Sat 23:45Z: 2026-12-05T00:00Z. Correct.
   - 30 min IST Sat/Sun from Fri 23:59 IST (18:29Z): 18:30Z, 19:00Z. Correct. Mon-only IST: Sun 18:30Z (= Mon 00:00 IST). Correct.
   - between 09:00-10:00 every 60: 09:00, 10:00 (end inclusive), next day 09:00. every 30 from exactly 09:30Z: 10:00Z (strictly after). Every 45 in 09:15-15:30 UTC: 14:15, 15:00, then next day 09:45 (grid not re-anchored). Correct. IST window case matches the dev's. Year end rolls to 2027-01-01T00:00Z. Correct.
4. Non-blocking, scheduler.ts:77-86 (overlap/run loop). Fake-clock sims, all behave as documented:
   - Single every-30 job with 70-min runs: starts 10:00, 11:30, 13:00 (always on grid, no drift); skipped slots logged per slot (10:30, 11:00; 12:00, 12:30; ...). No double run, no catch-up burst.
   - 5-min job with 12-min runs next to a 30-min job: a runs 10:00, 10:15, 10:30; skips 10:05, 10:10, 10:20, 10:25, ...; b still gets served between a's runs (no starvation: each pass of the for-loop visits every job, and a job's next due is strictly after its finish).
   - Cosmetic: the skip message says "previous run still active" whenever a slot fell in (due, finish]. If a slot was missed because ANOTHER job ran (job a due 10:00 but started 10:40 after a 40-min run of b), the log is slightly misleading, as the slot passed while a itself was waiting, not running. Suggest wording like "skipped (missed while busy)".
5. Non-blocking, cross-job interaction (item 3 of the brief). The loop is one sequential loop for ALL jobs; this is pre-existing on main. A `time` job B whose minute passes during job A's run is not skipped; it stays "due" and runs as soon as A finishes (late, no grace limit), and its next due is then computed from the finish time. Reproduction (jobs a time 10:00 runs 20 min, b time 10:15, c time 10:16 runs 30 min, fake clock): main and branch both give a 10:00, b 10:20, c 10:50, repeated next day, byte-identical (I diffed the logs by sha256, together with 3000 random `time`-job `nextRun` values: identical). So the branch does NOT change `time`-job behaviour. `everyMinutes` makes the delay more frequent: a 30-min job with 40-min runs (job a) next to daily `time` 10:15 (job b, 5 min): b starts 10:40 instead of 10:15 (late by one run of a, never skipped, never starved, since a's next start is the grid slot after its finish and b is visited in the same pass). The worst case delay of b is roughly one full run of one other job (the other job's timeout, default 600000 ms), per pass. Not blocking. Documented limitation + follow-up suggestion: (a) README sentence that jobs share one sequential loop so a long run delays other jobs' runs; (b) later, run jobs concurrently per job (one in-flight guard per job), or a max-lateness cutoff for `time` jobs.
6. Non-blocking, byte-identity (item 4). Against an origin/main build of my own: `--check`, `--next 4` and `--dry-run eod-review` on jobs.example.json (TZ=UTC): diff empty, same exit codes. 3000 randomised `time` schedules (random day sets, HH:MM, IST/UTC, random instants over 2026): `nextRun` output hash identical to main. The `main.ts` change is minimal and justified.
8. Non-blocking, README (item 6). The schedule table and "Interval schedules" paragraph match the code (inclusive ends, no overnight, grid not re-anchored, 7 -> 23:55 then 00:00). The TM2-73 line ("pre-TM2-74 alternative for a 30-minute cadence was external cron", example file left on daily `time`) is accurate. Two small gaps: the "Runs never stack" sentence should also mention the shared sequential loop (finding 5a), and the unreachable-window error from finding 1 should be documented once fixed.
