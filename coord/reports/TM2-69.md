# TM2-69 report: average holding time

## Root cause
`calc_metrics` in `bt-service/vibe_bt/backtest/metrics.py` published `avg_holding_days = trade_stats["avg_holding_bars"]`: the mean number of BARS held, labelled as days. On 1D bars the two coincide, so it was only ever right for daily data. On 1h bars it is hours (x24 overstated), on 1m bars minutes (x1440). Not an ns/us issue, not a denominator or span issue. The reported 16.2 "days" on 1h bars is really about 16.2 bars, i.e. about 0.68 days. Other places: `engines/base.py` trades.csv already writes `holding_days` from timestamps (`(exit-entry).days`, integer-truncated, untouched) and `holding_bars`; no API doc text states a unit other than the key name `avg_holding_days`.

## Fix (1 source file: bt-service/vibe_bt/backtest/metrics.py)
`win_rate_and_stats` now also returns `avg_holding_days`: mean of `(exit_time - entry_time).total_seconds()/86400` over trades (negative/invalid spans skipped), rounded to 4 dp. `calc_metrics` reports that as `avg_holding_days`. `avg_holding_bars` is unchanged. Being timestamp based it is correct for 1m, 1h, 1D and 24/7 crypto calendars. Caveat: for positions scaled into, the span runs from the first open (the old bars metric was lot-weighted); this matches trades.csv `holding_days` semantics.

## Review

Verdict: CHANGES REQUESTED (one blocking item: no test added; the fix itself is correct).

1. BLOCKING. No test was added. The brief requires the new `bt-service/tests/test_tm2_69_holding_time.py` with exact fixtures (3h/5h/2d) and the other metrics pinned. The diff touches only `bt-service/vibe_bt/backtest/metrics.py` and the report. No test in `bt-service/tests` references `avg_holding_days`, `calc_metrics` or `win_rate_and_stats` directly, so the old bug and this fix are both unpinned, and the report's "no existing test pinned the wrong value" is just that. The report's fixture/before-after tables rest on a scratchpad script that is not in the repo.
2. Not blocking. Root cause confirmed: the old line was `avg_holding_days = trade_stats["avg_holding_bars"]` (now metrics.py:894). It is the only computation of `avg_holding_days` in the repo. Repo-wide grep finds no other surface: no API schema, doc, agent-runner or trade-mcp code names it. `trades.csv` `holding_days` (engines/base.py:~2512, `(exit-entry).days`, integer-truncated) is a separate per-trade field and stays untouched. The unit is now documented only in the docstring (metrics.py:437, "calendar days, fractional"), which matches the new value. Nothing else describes the unit.
3. Not blocking. Trade pairing. `entry_time` is `Position.entry_time`, set at the opening fill, and `exit_time` is the closing or reducing bar's timestamp (base.py:2185, 2335). Behaviours I ran or traced:
   - Open at end of backtest: force-closed with `exit_reason="end_of_backtest"` and a TradeRecord (base.py:1553). It is included in both bars and days, so the two are consistent. I ran an always-long signal over 2024-01-01 to 2024-08-01: 1 trade, avg_holding_days 212.0, which is the full span. Positions the market rules forbid liquidating (`unliquidated_positions`, base.py:1538) get no trade and are excluded from both metrics.
   - Reversal long to short in one bar (alternating 10-bar +1/-1 signal, no flat bar): 22 trades, avg 9.6364 days. The new trade's entry_time equals the previous exit bar, so the spans do not overlap and none is negative.
   - Partial closes (`target_rebalance`): each reduction emits its own TradeRecord with `entry_time=before.entry_time`. Each slice therefore spans from the first open to the reduction bar, so one scaled position contributes several trades with overlapping spans. The bars metric is lot-weighted per slice, so for scaled-in or partially reduced positions the days and bars metrics are no longer proportional. The dev flagged the scale-in half of this, and it is acceptable and matches `trades.csv`. I would add one line to the docstring or report saying days are first-open to exit per trade record.
   - A second small inconsistency: the bars filter (`holding_bars >= 0`) and the days filter (span >= 0) drop different trades, so the two means can use different denominators when bars are invalid. Edge case, not blocking.
4. Not blocking. Timestamps. I ran `calc_metrics` under `-W error` on pandas 3.1.1 with tz naive, UTC and Asia/Kolkata, at ns/us/s index units, with trades of 3h, 5h, 48h and a same-bar 0 span, plus an invalid negative span. All 9 combinations gave 0.5833 days (= 56h / 4 trades). A 0 span counts as 0; a negative span is skipped. `total_seconds()` is unit-independent. Mixed tz-aware vs naive raises TypeError, which the `except Exception` swallows, so that trade is skipped silently. NaT is skipped. All-invalid gives 0.0. The broad `except Exception` can hide bad data; acceptable and mirrors base.py's pattern, but a `logger.debug` would help.
5. Not blocking. "No other metric changes". My own before/after loaded main's metrics.py as a separate module and ran both on the same 200-bar hourly equity curve with the 5 trades above, for each tz and unit. The keys are identical and the only differing value is `avg_holding_days` (14.0 before vs 0.5833 after). Rounding: 4 dp is consistent with `profit_factor` and `profit_loss_ratio` (4 dp); `avg_holding_bars` is 1 dp and returns 6 dp. For 1m trades (0.0417 d for 60 min) 4 dp resolves to about 9 s, which is fine. Both the `trade_count == 0` empty path (metrics.py:917) and the `win_rate_and_stats` empty path return 0.0, consistent.
6. Not blocking. Verification. `uv run pytest -q -W error` on `tests/test_tm8_edge.py` (193 passed) and `tests/test_crypto_edge.py` (24 passed) gave no new warnings. Those are the only tests that run `calc_metrics` end to end. No unit test calls it directly (see 1). `bt-service/uv.lock` is unchanged in the diff. I did not run the full suite.
