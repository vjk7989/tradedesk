## Change
`trade-mcp/test/sandbox.edge.test.ts`: only the "50 sequential runs" test was rewritten (plus the
`node:v8` / `node:vm` imports it needs, the same ones the O-9 RSS-flat test uses).

- 5 warm-up runs, then 50 timed runs in a row; every run must be `{ ok: true, result: [1, i] }`
  (fresh context each run: the guest global counter never carries over).
- Memory flat: forced GC before/after, same tolerance as the O-9 200-run RSS-flat test
  (RSS < +64 MB, external < +32 MB).
- Handles flat: `process.getActiveResourcesInfo().length` ≤ baseline + 2.
- Degradation: median of the last 10 runs ≤ 2 × median of the first 10.
- Timeout: 12 000 ms (was the 5 000 ms default).

### Proof: a 1 MB/run leak fails (temporary harness edit, `leak.push(...)` after each timed run, reverted)
- `new Array(1 << 17).fill(i + 0.5)` (1 MB of JS heap per run): **FAIL** `rss growth: expected 67342336 to be less than 33554432`.
- `Buffer.alloc(1 << 20, 97 + i%26).toString("latin1")` (a flat 1 MB heap string per run): **FAIL** `rss growth: expected 57339904 ...`.
- `Buffer.alloc(1 << 20, i)` (1 MB external per run): **FAIL** `rss growth: expected 60084224 ...`.
- 0.5 MB/run, `new Array(1 << 16).fill(i + 0.5)`: **FAIL** `heapUsed growth: expected 25428888 to be less than 10485760`.
- Caveat: `"x".repeat(1 << 20) + i` passed. V8 builds `repeat` from shared rope (cons) strings, so it
  does not retain 1 MB per run. It is not a real 1 MB leak.
(RSS is asserted first, so it is the message reported when several limits are exceeded.)

### Proof: a 2 ms/run growing slowdown (binding sleeps `2·i` ms, reverted)
- **Alone: 5 of 5 FAIL.** For example, last10 100.8 vs first10 25.3 (limit 75.3), and 97.6 vs 19.4 (limit 69.4).
- **Under 2 full suites: 13 of 15 FAIL, 2 of 15 pass.** Under heavy load first10 rises to about 45–70 ms, so
  the `2·first10` term (not the floor) sets the limit. A 2 ms/run slowdown then exceeds it by only
  1–60 ms, for example 116.6 vs limit 115.9 and 133.1 vs limit 131.4. Two runs stayed under it,
  for example 139.2 vs a limit of about 125.
- This limit comes from the required `2·first10` term, not from FLOOR_MS: no floor value changes it.
  One option is a 1.5× multiplier. Healthy loaded ratios peaked at 1.16, the step case is covered by
  the floor, and all 15 loaded slowdown runs would then fail. It was not applied because the brief
  specifies 2×. This is left for the coordinator to decide.

## Round 3: degradation multiplier tightened from 2× to 1.5× (coordinator decision)
The brief said `median(last10) ≤ 2 × median(first10)`. TM2 tightened it to
`last10 ≤ max(1.5 · first10, first10 + 50 ms)`. Evidence from round 2:
- Healthy loaded ratios peak at 1.16.
- The 50 ms floor already covers a load step.
- With 2×, a 2 ms/run slowdown passed 2 of 15 under heavy load; on that data 1.5× would have caught all 15.
No other change: memory, handle and timeout limits are as in round 2.

Re-run with 1.5× (same machine; 2 full suites looping in scratch clones):
- **20 loaded runs: 20 pass, 0 fail** (1.6–2.9 s each, timeout 21 s).
- **2 ms/run slowdown under load: 26 of 27 FAIL, 1 pass.**
  - Formal batch of 12: 11 FAIL, 1 pass (run 11).
  - Diagnostic batch of 15: 15 FAIL. Lowest margin: last10 126.5 ms against a limit of 102.5 ms (first10 68.3 ms).
  - The run-11 pass had no diagnostics, so its first10/last10 values are unknown. The likely cause is
    load dropping between the first and last runs (a load suite finishing or restarting), which hides a
    slowdown in wall time. No threshold can separate that from a real slowdown; a CPU-time metric
    would, but it would not see the sleep-based simulation and changes what the test measures, so it
    was not done.
- **Load step (2 suites spawned at run 25): 12 of 12 pass.**
