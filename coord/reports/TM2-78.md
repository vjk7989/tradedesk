# TM2-78 report: encrypted off-site backups to GCS

## Design
- `deploy/backup-gcs.sh` (age only). age chosen: single binary, plain public-key recipient
  file, no keyring or trust db. Supporting one tool keeps the script simple.
- Fail fast (exit 2, as backup.sh usage errors): BACKUP_BUCKET unset or not a bare name,
  AGE_RECIPIENTS_FILE unset/unreadable/empty, bad BACKUP_PREFIX, age or gcloud missing.
- Flow: `mktemp -d` (700, umask 077) -> `backup.sh <tmp>/plain` -> `tar -cf - | age -R
  recipients -o <tmp>/out/<stamp>.tar.age` -> header check -> upload. EXIT trap removes the
  temp dir on success and failure. Runtime failures exit 1, as backup.sh.
- Remote retention: bucket lifecycle rule (documented). No KEEP_DAYS pruning: the upload-only
  SA (`roles/storage.objectCreator`) cannot list or delete, and giving the VM delete rights
  would let a compromised VM wipe backups. Documented.
- Test hook: `TRADEDESK_BACKUP_SH` overrides the backup.sh path.

## Never-unencrypted guarantees
1. gcloud is called from exactly one place, `upload_encrypted`, which refuses any file not
   named `*.tar.age`, any destination not `gs://*.tar.age`, and any file whose first 21 bytes
   are not `age-encryption.org/v1`.
2. Plaintext tar is piped straight into age; the only plaintext on disk is backup.sh's own
   output inside the 700 temp dir. If age fails the partial output is deleted and the
   script exits before upload.
3. Placeholders only; logs print paths and bucket/object names, never key material or file
   contents.

## Review
Reviewer: independent, head e374443. Verdict: **CHANGES REQUESTED** (one blocking finding, 1; the rest are non-blocking).

Checks run: `bash -n` OK; shellcheck (via `uvx --from shellcheck-py shellcheck -S style`) clean; `uv run --with pytest --with pyyaml pytest -q deploy/` gives 3 failed, 365 passed, 24 skipped, 25 errors (the 28 known docker-less cases, nothing new); `backup.sh` and `restore.sh` are unchanged vs main. No real GCS or age was available, so GCS behaviour below is from Google's docs plus reasoning, not an end-to-end run.

1. **BLOCKING. deploy/backup-gcs.sh:46 and docs/backup.md:96-101: objectCreator alone breaks uploads of 150 MiB or more.** Google's "Parallel composite uploads" doc states that `gcloud storage cp` enables parallel composite upload by default (`storage/parallel_composite_upload_enabled` default None means enabled, threshold 150 MiB). Composing needs `storage.objects.get` and deleting the temporary components needs `storage.objects.delete`, and objectCreator has neither. The doc's troubleshooting section describes exactly this: "Uploads of files smaller than 150 MiB succeed, but uploads of files 150 MiB or larger fail with HTTPError 403: ... does not have storage.objects.get". With the default compatibility check on, gcloud probes the bucket first and may fall back to a plain upload, but that probe is not guaranteed to work with objectCreator, and the failure would hit exactly when the audit log has grown. Plain single-object and resumable uploads need only `storage.objects.create`, so small backups should work. Fix (one line, keeps least privilege): before the gcloud call add `export CLOUDSDK_STORAGE_PARALLEL_COMPOSITE_UPLOAD_ENABLED=False` (equivalent to `gcloud config set storage/parallel_composite_upload_enabled False`), and mention it in the docs. Do not use `--no-clobber` (needs get/list) and do not add delete. The unique timestamped name already prevents clobber, and objectCreator cannot overwrite anyway. Also: please do one real smoke test on a scratch bucket with objectCreator only, with a small file and a file above 150 MiB (`head -c 200M /dev/urandom > x.tar.age` style is not valid age, so test with the script and a padded backup or with raw `gcloud storage cp` plus the env var). I could not confirm from docs that destination-path resolution never needs `storage.objects.list`/`get`; the shims cannot show it.

2. Never-unencrypted (all OK). `gcloud` appears only at :29 (`command -v`) and :46 inside `upload_encrypted`, which is called once (:71). The suffix checks (:41-42) and the 21-byte magic check (:44-45; `${#AGE_MAGIC}` is 21) are on a file only `age` writes, inside a 700 dir created by `mktemp -d` under umask 077, so a symlink or race needs a same-uid attacker, who already owns the plaintext. A partial file is not a concern because the `age` failure path deletes it (:66) and `pipefail` (:13) makes `if ! tar | age` fail on a tar error, so a truncated-but-valid archive is not uploaded. `[ -f ]` follows symlinks but there are none here. The magic check is a sanity check, not a proof of encryption; the real guarantee is that the only producer is age. Non-blocking.

3. Non-blocking. Plaintext cleanup, deploy/backup-gcs.sh:34-36. The EXIT trap covers all `exit` and `set -e` paths, and bash also runs it on SIGINT/SIGTERM/SIGHUP (after the foreground child ends); I reasoned this and did not test it. SIGKILL, OOM kill or power loss leaves a plaintext backup in `$TMPDIR` (700, root). Suggest putting the temp dir under a root-only directory such as `/var/lib/tradedesk-backup/` (or `systemd` `PrivateTmp=true` plus `StateDirectory`), noting that `/tmp` may be tmpfs (RAM) and the plaintext is about one full backup in size.

4. Non-blocking. Recipient file, docs/backup.md:123-124. `age -R` also accepts plugin recipients (`age1<plugin>1...`) which run `age-plugin-*` binaries from PATH, so anyone who can write that file, its directory, or PATH can redirect encryption to their key. Add one sentence: the recipient file and `/etc/tradedesk` must be root-owned and not group/world-writable (the doc uses `chmod 644`, fine if root-owned; add `sudo mkdir -p /etc/tradedesk` since `tee` fails without it), and the owner should compare the printed public key with the offline key. Optionally have the script refuse a recipient file not owned by the running uid or with group/other write bits.

5. Non-blocking. `TRADEDESK_BACKUP_SH`, deploy/backup-gcs.sh:10,17. It is read from the environment; under the documented unit that is only the root-owned 600 `EnvironmentFile`, and whoever controls that file can already set `AGE_RECIPIENTS_FILE`, so it adds no new privilege. It is not in docs/backup.md (good); keep it that way, and note in the header that it is test-only. A `sudo -E` or a wrapper that inherits an attacker-set env would run an arbitrary program as root, but that is true of every variable here. It cannot bypass encryption since the upload path is unchanged.

6. Non-blocking. Docs gaps, docs/backup.md.
   - age is not installed anywhere in the steps (`sudo apt install age`; available in Debian 12/Ubuntu 22.04 and later; check `age --version`). The `config` exit 2 appears otherwise.
   - systemd timezone suffix in `OnCalendar` needs systemd 235 or newer: Ubuntu 16.04 (229) does not support it; Ubuntu 18.04 (237), 20.04 (245), 22.04 (249), 24.04 (255, verified locally 255.4), Debian 10 (241), 11 (247), 12 (252) do. Add that and `systemd-analyze calendar '*-*-* 02:30:00 Asia/Kolkata'` to verify.
   - The 30-day lifecycle also deletes your last good backups if uploads silently stop; add an alert or a weekly check that the newest object is under 2 days old (objectCreator cannot list, so this needs the reader identity).
   - Changing the VM service account to the uploader removes the default compute SA's other scopes (logging, Artifact Registry pulls); say so or add `--scopes storage-rw,logging-write`.
   - Versioning note is right but with objectCreator no overwrite happens, so versioning adds nothing; consider a bucket retention policy instead.
   Everything else asked for is covered: uniform access and public access prevention (:79-80), lifecycle (:81-87), objectCreator on the bucket only (:92-98), age key generated off the VM with only the recipient on it (:115-127), 600 env file, `flock -n`, `Persistent=true`, restore drill with a separate read-capable identity (:170-182). Placeholders only. docs/gcp-deploy.md change is a single pointer paragraph (4 lines), one step only: OK.

7. Exit codes: 2 for config (:24-32), 1 for runtime (backup, encryption, upload, wrong dir count) consistent with backup.sh. gcloud stderr is not suppressed (stdout only), so permission errors will be visible in the journal. OK.

Required to approve: finding 1 (disable parallel composite uploads in the script and document it, plus one real objectCreator-only smoke test). Findings 3-6 are recommended follow-ups.
