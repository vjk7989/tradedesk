## What changed
- **Platform-aware per-sample CPU floor:** `minSampleMsFor(platform, threadCpu)` returns 60 ms when `process.threadCpuUsage` exists and the platform is not win32, which gives µs resolution. It returns 200 ms on win32 or with the `process.cpuUsage()` fallback.
  - The test asserts this mapping for win32/linux/darwin × threadCpu yes/no, so the win32 ≥200 ms floor is pinned by code path.
  - `costRatio(small, large, minMs = MIN_SAMPLE_MS)` takes the floor as a parameter, which is what the win32 simulation below uses.
- **k growth:** the "≤ 2 ticks, grow ×4" rule assumes a 15.6 ms tick only on the 200 ms path. On the 60 ms path it assumes 1 ms, so k is estimated from the cost sooner and samples overshoot the floor less. The estimate margin changed from 1.3 to 1.2.
- **REPS:** changed from 9 to 7, median of interleaved small/large samples after one warm-up of each. The spread is tight (tables below), so 7 is enough.
- **Call-count workload:** still 500 vs 10k checks (20×), now against the 250-date list instead of the 5000-date one.
  - Reason: with 5000 dates, one 10k-check run cost ~600-800 ms of CPU and dominated the test time.
  - It also diluted a per-call growth term behind the 5000-entry scan. TM2-52's quadratic proof only reached ~100×; it now reaches ~164×.
  - Dependence on list length is still covered by the separate "checks vs list length" ratio.
- **Kept unchanged:**
  - all 3 ratios (parse 250 vs 5000 dates; checks vs call count; checks vs list length 100 checks × 250 vs 5000);
  - `MAX_RATIO = 30`;
  - the `cpuUsage` fallback and no skip;
  - the functional asserts (5000 parsed, NSE open, an added 2026-01-26 closes it);
  - the 300 s timeout.
- **Diagnostics:** `TM3_PERF_LOG=1` prints one JSON line per ratio with per-run costs, k, sample CPU ms and wall ms. It is off by default.

## O(n²) proof (in-test only, each reverted; `diff` against the saved final file clean after each)
Each variant was run 2 times and failed 2 of 2 times:
- **Parse:** each parse is followed by an `indexOf` de-dup of both parsed lists.
  `parse: large 497.169 / small 3.222 CPU ms per run = 154.3x`, then 158.6x.
- **Checks vs call count:** each check also scans a growing `seen` array of all prior keys (`if (!seen.includes(key)) seen.push(key)`).
  `checks vs call count: large 457.939 / small 2.799 CPU ms per run = 163.6x`, then 164.1x.
- **Checks vs list length:** each check first de-duplicates the whole holiday list with `L.filter((d, j) => L.indexOf(d) === j)`.
  `checks vs list length: large 18978.136 / small 48.994 CPU ms per run = 387.4x`, then 383.6x.
