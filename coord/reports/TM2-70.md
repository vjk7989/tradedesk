# TM2-70 report: tz-explicit point-in-time joins (no look-ahead from tz mixing)

## Change
- New `bt-service/vibe_bt/backtest/loaders/pit_calendar.py`: `market_calendar_index(index, tz)` (naive: returned unchanged; tz-aware: `tz_convert(tz)` then `tz_localize(None)`) and `assert_clean_datetime_index(idx, where, monotonic=)` raising `PitCalendarError`.
- `fundamentals_loader.py`: `_ffill_pit` keys the bar index by US/Eastern, guards the union, restores the caller's index; tz-suffixed `filed` handled; `_extract_concept_series` (was :103-105) now parses with `format="ISO8601"` via `_parse_iso_dates` (mixed tz/naive falls back to per-value parse, tz-aware -> NaT, as `_ffill_pit` already did).
- `industry_loader.py`: day keys from Asia/Shanghai wall clock instead of UTC epoch.
- `rsshub_events.py`: bar dates from Asia/Shanghai calendar date instead of the index's own wall clock; tz-aware `as_of` boundary capped at its CN date.
- `tushare_fundamentals.py` untouched (not refactored; its inline rule is already identical in effect and a refactor would add risk for no gain).

## Per-loader rule (naive index = already market-local, as today)
| Loader | Market tz | Reason |
|---|---|---|
| `_ffill_pit` (SEC) | America/New_York | EDGAR `filed` is an Eastern calendar date. Tz-aware bars -> ET wall clock. Tz-suffixed `filed` -> `max(stated wall-clock date, ET date of the instant)`: never earlier than either reading, so it can only delay, never advance, visibility. |
| industry | Asia/Shanghai | Tushare `in_date`/`out_date` are CN-local dates; comparing the UTC epoch of an aware index against them shifted every boundary by 8h. |
| rsshub | Asia/Shanghai | `knowable_date` uses the A-share close cutoff (16h) so it is a CN-local date. `_knowable_date` (pubDate) is deliberately unchanged: tests/test_tm11_edge.py pins "wall time is kept" for tz-aware pubDate. `as_of` aware: `min(displayed date, CN date)`, so a boundary east of CN cannot admit tomorrow's items; west-of-CN behaviour unchanged. |

## Guard design
`pit_calendar.assert_clean_datetime_index` is called after every key construction/union: it raises `PitCalendarError` (RuntimeError) if the index is not a `DatetimeIndex` (object dtype), is tz-aware, or (with `monotonic=True`, used on the `_ffill_pit` union before `ffill`) is not monotonic increasing. `_ffill_pit` checks the filed keys and the union; industry and rsshub check their bar keys. tz-aware indexes with repeated wall-clock times (DST fall-back) use unique keys for the union and are re-reindexed onto the caller's exact index; naive path is untouched (still raises on duplicate labels exactly as main did).

## Review
Reviewer: independent adversarial review. Verdict: **CHANGES REQUESTED** (1 blocking, waivable by the owner with an explicit decision; the rest is non-blocking).

### Findings
1. **BLOCKING (owner may waive): rsshub tz-suffixed `pubDate` still gives a one-day look-ahead.** `rsshub_events.py:297` (`_knowable_date`) drops the tz and keeps the wall clock. I ran it end to end through `query_events` and `_parse_items`: `Fri, 05 Jan 2024 10:00:00 GMT` (18:00 CN, after the 16h cutoff, so it should be knowable 01-06) gets `knowable_date` 01-05 and is visible to a CN bar on 01-05. `10:00:00 -0500` (23:00 CN) also gets 01-05. RSSHub and most RSS feeds emit GMT. This is exactly "a tz-suffixed source date, value before its PIT date", which the acceptance criteria cover. The dev left it because `tests/test_tm11_edge.py` pins "wall time is kept". Suggested fix, mirroring SEC: for a tz-aware `published`, take `max(wall-clock knowable date, knowable date of the instant converted to Asia/Shanghai)`. Never earlier than either reading. Note a plain CN conversion would be EARLIER for east-of-CN offsets (+09:00 16:30 becomes CN 15:30), hence the max. The test writer updates the tm11 pin. If the owner waives it, it must be a written follow-up ticket.
2. **Non-blocking (regression vs main): guard false positive on a naive index containing NaT.** `fundamentals_loader.py:262-263`. `_ffill_pit` with a naive index `[2024-01-04, NaT, 2024-01-06, ...]` works on main (float64 result). On the branch the union is "not monotonic" (NaT) and `PitCalendarError` is raised. Degenerate input, and the failure is loud and safe, but it contradicts "naive byte-identical". Either exempt NaT (check monotonic on `union.dropna()`) or state it in the report. Nothing else I tried raised on naive input.
3. **Non-blocking: the guard error is swallowed upstream.** `runner.py:1222` (`_inject_fundamental_panel`) catches every exception, logs a warning and injects NaN frames, so a `PitCalendarError` there degrades to NaN factors rather than failing the run. This is safe (NaN, not look-ahead), but it is not "raise a clear error". Consider re-raising `PitCalendarError` there.
4. **Non-blocking (intraday granularity, pre-existing): date-keyed sources are visible from 00:00 of the PIT date.** A filing dated 01-05 (ET) shows on a 01-05 09:30 1h bar even if it was filed at 20:00 ET. The same for rsshub `knowable_date` and industry dates. Same as main for naive; not a tz bug. Document it.
5. **Non-blocking (rsshub, non-CN assets): a tz-aware UTC index now keys by the CN date.** `rsshub_events.py:593-598`. `event_feeds` is not market-gated (`engines/base.py:519-535`), so a crypto backtest with UTC-aware hourly bars can reach it. Bars 16:00Z-23:59Z (= CN next day) now see events knowable on the next CN date, up to 8h earlier than on main (which used the UTC wall date). Naive input is unchanged. Impact is limited (opt-in feeds, CN-oriented) but it is earlier-than-main for aware non-CN indexes; document it or gate on market.
6. **Non-blocking (SEC tz choice): US/Eastern is right for EDGAR `filed`** (acceptance is stamped in Eastern; the dates are Eastern calendar dates). It is conservative for any index east of ET (UTC, CN, IN: ET date <= local date, filings only appear later). **Not conservative for a tz-aware index west of ET** (e.g. America/Los_Angeles bar at 22:00 PT on 01-04 = ET 01-05 01:00 sees a 01-05 filing that is not yet filed in PT terms). I tested LA indexes and they are consistent with the ET rule, so this is by design. Practically irrelevant (US equity bars are ET or UTC).
7. **Non-blocking: mixed-offset tz-suffixed `filed` strings (e.g. Z with +05:30 in one frame) silently drop to NaT** with one warning (`fundamentals_loader.py:~228`, same on main). Safe (data loss, not look-ahead). Also a mixed `Z`/`+00:00` pair now correctly returns [nan, 2, ...]; on main it returned 2.0 from 01-04 (look-ahead).
8. **Non-blocking: the branch is 9 commits behind main** (`git rev-list HEAD..origin/main` = 9). The merge-base diff is clean (4 files + report), but merge or rebase before merging.
9. Asia/Shanghai is correct for Tushare `in_date`/`out_date` (CN calendar dates; no DST). rsshub: the 16:00 cutoff is the existing A-share convention (close 15:00), unchanged and fine for CN; the `as_of` cap `min(displayed, CN date)` is correct: only ever earlier, never later (`+09:00 01-05 00:30` now excludes 01-05 items; it admitted them on main). Naive `as_of` unchanged.
