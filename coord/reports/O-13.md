# O-13 report: in-run memory check for native-call loops

## Root cause (measured)
Repro: 16 MB cap, guest builds a ~4 MB JSON string (150k objects) and loops `JSON.parse` 300 times, logging after each. Before the fix all 301 logs were written (36 s) and the error came only from the post-run check.
Direct runtime measurement (parse and discard):
- Q1, is `setMemoryLimit` accounting it? Yes, but only for live objects: `computeMemoryUsage().memory_used_size` stayed at 14 MB (under 16 MB). The limit is not the problem.
- Q2, interrupt frequency? This is the cause. The interrupt handler was called 0 times during 40 parses (16 calls in total, all during setup). QuickJS polls it every ~10k back-edges/calls, and a loop of a few large native calls runs far fewer bytecodes.
- Q3, fragmentation? Partly. The WASM linear memory went 16 -> 33 -> 48 MB while live objects stayed at 14 MB. The growth is the transient copy of the source string, parse buffers and freed-but-unreturned blocks. Linear memory never shrinks, so the peak is what counts. It exceeds the 32 MB ceiling (cap + 16 MB), and nothing looks at it until the run ends.

## Fix (quickjs.ts)
The guest `JSON.parse` is wrapped (installed once, original kept in a closure). After each parse of a string over 16 KB, a host `guard()` runs the ceiling check. If exceeded, it sets `memoryExceeded` and the wrapper throws, ending the run. A guest that catches the error still ends with "memory limit exceeded" (interrupt handler at its next poll, or the post-run check). The cheaper alternatives did not work: the interrupt rate is not configurable, and a check per binding call never runs in a loop with no binding calls.
Side fix required: the argument-size snapshot swallowed every guest error as "not serialisable". The wrapper shifted heap by a few bytes, so an out-of-memory in an existing O-9 test was reported with the wrong message. It now rethrows `InternalError` (out of memory/stack), which restores "binding argument too large". No test edited.

## Overhead
Normal script (3000 small parses + 400k-element arithmetic loop), median of 25 runs, 3 repeats each: with fix 39.1-39.9 ms, without 39.7-42.9 ms: no measurable change (<5%). Without the 16 KB threshold the guard cost ~5.6 us per parse (+50% on a parse-heavy script), hence the threshold.

## Result
- New test: log stops at <10 of 300 (fails before the fix); swallow-the-error case; behaviour check (reviver, SyntaxError, `length` 2).
- vitest: 2268 passed, 4 failed (known `tm2_35` Windows failures, not O-13). tsc and build pass.
- Limitation: other native allocators (`'x'.repeat`, `Array.join`, ...) are not guarded; only JSON.parse is, as in the finding.
