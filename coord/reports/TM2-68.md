## Choice: `format="ISO8601"`
Every source is ISO-8601. ISO8601 parses date and date-time strings per element (no first-string inference) and does not guess day/month order for ambiguous strings, whereas `"mixed"` would (verified: `"01/05/2024"` -> 2024-01-05 under `mixed`, NaT under `ISO8601`). Non-ISO input is therefore flagged by the warning rather than silently guessed. datetime64 (s/ns checked), object Timestamps and `None` still work.

Note (out of scope, not changed): `fundamentals_loader.py:105` (and 103-104) still use inferred `to_datetime(errors="coerce")` on raw SEC strings; SEC always emits `YYYY-MM-DD` so it is not currently lossy, but the same pattern could be hardened in a follow-up.

## Fix round 1
Correction: the earlier claim that main also raises on mixed tz-aware/naive strings was wrong. Main coerces `["2024-01-03","2024-01-04T16:30:00Z"]` to `[2024-01-03, NaT]` without raising; the first patch raised `ValueError: Mixed timezones detected`.

Fix (fundamentals_loader.py only): the `to_datetime(format="ISO8601", errors="coerce")` call is wrapped in `try/except ValueError`. On failure each value is parsed individually by `_parse_naive_filed`: naive ISO values are kept, tz-aware values (or anything unparseable) become NaT. They are then counted in the existing single warning. No `utc=True`; the dtype stays datetime64[us]. The normal path is untouched.

Results (index 2024-01-02..08):
- `["2024-01-03","2024-01-04T16:30:00Z","2024-01-05 10:00"]` values 1,2,3: no raise, `[nan,1,1,3,3]`, one warning "dropped 1 ... examples: '2024-01-04T16:30:00Z'".
- `["2024-01-04T16:30:00Z","2024-01-03"]`: no raise, one warning, naive value kept.
- Uniformly tz-suffixed (all Z): no raise, no warning, same path as before this fix (parses tz-aware; the later union with the naive target index gives an odd result, `[2,2,2,2,2]` in my script). Behaviour unchanged by this round and not addressed here; since no source emits tz-suffixed strings it is unreachable today.
- All-ISO/naive proof re-run (eq.py, 6 frames): hashes identical to main and to round 0. Mixed date/datetime and unparseable cases give the same output and the same single warning as before.

### All-tz-suffixed finding (main vs branch)
Input `["2024-01-03T00:00:00Z","2024-01-05T00:00:00Z"]` (values 1, 2) against naive index 2024-01-02..05, 08:
- origin/main: `[2,2,2,2,2]`
- branch: `[2,2,2,2,2]` (identical; same for `+05:30`)

This is look-ahead (the 01-05 value appears on 01-02..04) and it is pre-existing, not introduced by TM2-68. Cause: the parsed `filed` index is tz-aware (UTC), so `values.index.union(target_index)` becomes an unsorted object Index (tz-aware stamps first, naive after); `ffill` then carries the last tz value onto every naive target and `reindex(target_index)` picks those. Unreachable today (no source emits tz-suffixed `filed`), but encoded as a strict xfail pointing at the TM2-69 proposal (fix: strip or convert tz to naive before the union, or reject tz-aware `filed`).

Related, from the same probe: on main, mixed tz input with the tz value first (`["2024-01-04T16:30:00Z","2024-01-03"]`) gives `[1,1,1,1,1]`, i.e. the tz value leaks onto 01-02 (look-ahead); the branch gives `[nan,2,2,2,2]` plus a warning.
