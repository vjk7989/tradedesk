# TM2-46 report: DATA_DIR lock; revoke-all refuses a live server

## What changed
- `trade-mcp/src/datadir-lock.ts` (new): `DATA_DIR/trade-mcp.lock` = JSON `{pid, startedAt, hostname, procStart}`, created with exclusive create (`wx`).
- `trade-mcp/src/index.ts`: HTTP mode acquires the lock before listening (refuses with a clear message and exit 1 if live); releases it in the SIGINT/SIGTERM handler path (process exit hook). `--stdio` mode does not lock.
- `trade-mcp/src/oauth/revoke-cli.ts`: checks the lock before touching the store.
- `trade-mcp/test/tm2_46_datadir_lock.test.ts` (new): 12 tests. No existing test edited; none starts two servers on one DATA_DIR (the existing tests use `createHttpServer` directly, never `index.ts`).

## Lock states (decision table)
| lock content | state | server start | revoke-cli --force |
|---|---|---|---|
| missing | missing | create | proceed |
| same hostname, pid alive, procStart matches (or unavailable) | live | REFUSE | REFUSE, exit 4 |
| same hostname, pid dead | stale | replace + log | proceed (note) |
| same hostname, pid == own pid | stale (previous incarnation) | replace + log | proceed |
| same hostname, pid alive but /proc start time differs (pid reuse) | stale | replace + log | proceed |
| different hostname | foreign | replace + log (assumed dead) | proceed with a warning |
| unparsable | corrupt | replace + log | proceed (note) |

Crash (SIGKILL): the lock stays; the pid is dead, so the next start replaces it (tested with a real killed process). Clean shutdown removes the lock only if it is still ours (pid, startedAt, hostname).

## Exit codes (revoke-cli)
0 ok/nothing to revoke; 1 corrupt or wrong-shape store; 2 usage (missing `--force`, unknown arg); 3 unexpected error; **4 trade-mcp is running** (new). Message: "trade-mcp is running; stop it first (...). --force does not override a live lock."

## Container pid-namespace design
`docker compose run --rm --no-deps` creates a NEW container: new hostname (container id) and new pid namespace, where the CLI may itself be pid 1. So a pid check alone is meaningless across containers. The design:
- Hostname is part of the lock. A lock whose hostname differs from ours is "foreign", and we never trust a pid check for it (pid 1 in the old container would look alive, or be ourselves).
- Same hostname = same container (including `docker compose restart` and in-container crash restarts, where the server is pid 1 again): the pid-equals-self rule treats that as the previous incarnation, and the /proc start-time comparison defends against pid reuse.
- For the CLI, a foreign lock is treated as stale ONLY because `--force` asserts the runbook step `docker compose stop trade-mcp` was done; it prints a warning. The documented flow (stop, run, start) therefore works, and the lock left by the stopped container (clean exit removes it; a kill leaves it) never blocks it.
- For server start, a foreign lock is likewise replaced (otherwise a SIGKILLed container that is recreated, with a new hostname, could never start again).

## Honest limits
- The lock can detect a live server only in the SAME pid namespace and hostname: a process on the same host, or the same container. This is the case for running the CLI via `docker compose exec` (same container) or a bare-metal run.
- It CANNOT detect a live server in ANOTHER container sharing the volume (e.g. `docker compose run` while trade-mcp is still up, or two compose projects on one volume). There the lock is "foreign" and the CLI proceeds under `--force`, with only a warning. The protection against that case remains the runbook (`docker compose stop` first; `docker compose ps` to confirm). Likewise a second server started in another container on the same volume would replace the first's lock.
- Hostname can be overridden (`hostname:` in compose); two containers with identical hostnames would defeat the foreign/same distinction (then the pid check applies and may misjudge).
- Races: acquisition is atomic (exclusive create); stale replacement is unlink-then-create with a retry loop, so two simultaneous starters on a stale lock end with one winner. Reading the lock in the CLI and then writing the store is not atomic against a server starting in between.
- Lock is advisory: nothing stops code writing oauth.json directly.
- `/proc/<pid>/stat` start-time check is Linux-only; elsewhere it is skipped.

## Fix round 1
Implements the Opus fix plan (review MEDIUM-1..4, LOW-1). Files: `trade-mcp/src/datadir-lock.ts`, `trade-mcp/src/index.ts` (start, shutdown, heartbeat), `trade-mcp/src/oauth/revoke-cli.ts`, `docs/vps-runbook.md` §13. No tests edited.

Behaviour changes
- Atomic acquire: lock JSON is written to a tmp file and `linkSync`ed to `trade-mcp.lock` (exclusive, never half-written). Stale replacement is serialised by a short-lived guard file (`trade-mcp.lock.replace`, stale after 10 s), re-judged under the guard, renamed aside, verified to be the lock judged stale (else restored), then we link our own. Bounded retries; clear "could not acquire" error.
- Empty or unparseable lock younger than 5 s (mtime) counts as live; older is corrupt and replaced. Unreadable lock (EACCES on read) counts as live (fail closed).
- Heartbeat: the server `utimesSync`s the lock every `HEARTBEAT_MS` = 5000 on an `unref()`'d interval, cleared on shutdown. A lock with mtime younger than `LIVE_WINDOW_MS` = 15000 is live regardless of hostname/pid. "foreign" is no longer returned: a foreign lock is live (fresh) or stale (old). Same-host rules unchanged (own pid, dead pid, reused pid = stale), so a same-container restart is immediate.
- revoke-cli checks the lock FIRST: live gives exit 4 with or without `--force` ("trade-mcp is running (lock heartbeat Ns ago); stop it first, then wait 15 s"). Usage/--force checks (exit 2) come after.
- DATA_DIR not writable: EACCES/EROFS/EPERM fail at startup with a one-liner naming the lock path (`LockUnwritableError`, has `.code`); this is a startup behaviour change vs main (previously failed at first audit/risk write). ENOSPC warns and continues without a lock.
- Runbook §13: exit code 4, wait ~15 s after `stop`, trade-off note.

Documented trade-off: after a crash or SIGKILL, a NEW container (different hostname) may wait up to 15 s before it can start; compose `restart:` retries cover this. Same-container restart is immediate.

Known limit: the stale-replace window cannot be closed to zero without an OS lock; the guard plus re-judge under the guard leaves only a release-during-replace window.
