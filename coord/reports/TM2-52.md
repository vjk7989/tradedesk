## Cause
The old test asserted `parse + 10k checks < 3000 ms` of wall-clock time. `isMarketOpen` does `holidays.NSE.includes(date)`, which is a 5000-entry scan per check, so 10k checks take about 50M string compares (~0.55 s on a quiet machine). Under load, wall time includes time spent descheduled, so the loaded p99 reached 2.2 s, close to the 3 s limit.

- **thread CPU time** medians (final): checks **18.9 / 20.2 / 21.5x** (min/p50/max), parse **8.5 / 14.7 / 18.2x**.

## Bound chosen
- Cost = `process.threadCpuUsage()` (user+sys) of the test thread. Load delays the thread but adds no CPU time to it.
- Each size is the median of interleaved reps after one warm-up of each: checks use 5 reps, 500 vs 10,000 checks against the 5000-date list; parse uses 15 reps, 250 vs 5000 dates per group through `loadConfig`.
- Assert `large / small <= 30` for both. Linear is ~20x and O(n^2) is ~400x. The measured max is 21.5x under load, which leaves 1.4x headroom, and the limit sits far below quadratic. The functional asserts are unchanged (5000 parsed, the date is open, an added 2026-01-26 closes it). No skip. The failure message prints both CPU medians and the ratio.
