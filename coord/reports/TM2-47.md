# TM2-47 report: container memory/CPU limits

## Change
`mem_limit` per service in `deploy/docker-compose.yml`, env-driven with defaults; `deploy/.env.example` and `docs/vps-runbook.md` (sections 1 and 5) document them; new `deploy/test_tm2_47_limits.py` (7 static tests).

| Service | Var | Default |
|---|---|---|
| openalgo | OPENALGO_MEM_LIMIT | 1g (no upstream recommendation found; covers the 512 MB shm_size) |
| trade-mcp | TRADE_MCP_MEM_LIMIT | 768m |
| bt-service | BT_MEM_LIMIT / BT_CPUS | 1g / 1 (unchanged values, now overridable) |
| caddy | CADDY_MEM_LIMIT | 128m |

Sum = 768 + 1024 + 1024 + 128 = 2944 MB <= 3072 MB (3 GB); about 1 GB left on a 4 GB VPS. `restart: unless-stopped` kept on all services (an OOM kill exits 137, which the policy restarts). trade-mcp port still unpublished.

## Measurements (local, Linux, Node 22)
- trade-mcp `node dist/src/index.js` (MODE=paper, fake tokens, unreachable OPENALGO_URL, temp DATA_DIR): RSS 100 MB after startup, 101 MB after an MCP client connected.
- During `execute` calls (array-building loops): peak 187 MB over 6 sequential runs, 212 MB peak with 4 concurrent runs (light workloads, so below the worst case).
- bt-service walk-forward on fixture btc_1d.csv (docs/backtesting.md example: 60/30 days, 3 candidates, 2024-01-01..2024-08-01, source=local): 15 MB after import, peak 282 MB for the whole process tree (parent + backtest child), 187 s wall. 1g leaves about 3.5x headroom.

## trade-mcp arithmetic (ADR-19 formula)
worst case = base + N x (memoryBytes + 32 MB) = 100 + 4 x (64 + 32) = 484 MB. memoryBytes default 64 MB (`trade-mcp/src/sandbox/quickjs.ts`). Default 768 MB >= 484 MB with ~284 MB headroom for the V8 heap and binding copies. Branch merged with main (#77, ADR-19).
