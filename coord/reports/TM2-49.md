## Test changes

### `trade-mcp/test/tm2_35_revoke_all.edge.test.ts`
1. **`runProc` spawns `process.execPath --import tsx <cli.ts>` with `cwd: ROOT`.** It used to run `node_modules/.bin/tsx`, which is a `sh` shim on POSIX and `tsx.cmd`/`tsx.ps1` on Windows. `spawnSync` without a shell cannot run either shim on Windows, so it returned `status: null`. The new form matches the tm2_46 edge tests and needs no shell.
2. **`it.skipIf(IS_WIN)` on the four read-only DATA_DIR tests**, because NTFS ignores POSIX mode bits and `chmod 0o555` on a directory does not stop file creation. The tests are:
   - "write failure (read-only DATA_DIR) in a real process …"
   - "read-only DATA_DIR: original store byte-identical … (real process)"
   - "read-only DATA_DIR in-process …"
   - "read-only DATA_DIR exits 3 (real process) …". This is the owner's "expected null to be 3".

These two changes account for the owner's 4 failing tm2_35 tests:
- exit-3 read-only (skipped on Windows);
- in-process read-only (skipped on Windows);
- "success path (in-process and real process)" (spawn fixed);
- "real process exit codes match in-process" (spawn fixed).

**However**, the real-process tests also need source fix S1 below. Until then they get exit 0 with no output on Windows.

`tm2_35_revoke_all.test.ts` needed no change. It runs in-process and already uses `os.tmpdir()` and `path.join`. Its output asserts use `toMatch`/`toContain`, so line endings don't matter.

### `trade-mcp/test/tm2_46_datadir_lock.test.ts`
3. **`sleeper()` spawns `process.execPath -e "setTimeout(…,60000)"` instead of `sleep 60`.** Windows has no `sleep.exe`. The spawn fails with ENOENT, so `pid` is undefined and the lock is written without a pid.
4. **`it.skipIf(IS_WIN)` on "pid reuse (live pid, different process start time) is stale".** This case can only be detected through `/proc/<pid>/stat`.

### `trade-mcp/test/tm2_46_datadir_lock.edge.test.ts`
5. **`liveOther()` uses a node child instead of `sleep 120`.** Same reason as change 3.
6. **`deadPid()` uses `process.execPath -e "process.stdout.write(String(process.pid))"` instead of `sh -c 'echo $$'`.** Windows has no `sh`, so `stdout` was null and `.trim()` threw. On Windows, `process.kill(pid, 0)` on an exited child gives ESRCH (libuv checks `GetExitCodeProcess`), so "dead" still holds.
7. **New `procStartIfAny(pid)`.** It returns `procStartOf(pid)` on Linux and `undefined` on win32. `liveLock()` and the own-pid `classify` assertion use it. Before, every test that built a live lock threw ENOENT on `/proc` on Windows, which is most of the owner's 25 tm2_46 failures. On Linux the value is identical. Tests compare with `toEqual`, which ignores an `undefined` `procStart`.
8. **`skipIf(IS_WIN)` on the three symlink tests** (live target, stale victim, dangling). `symlinkSync` needs admin rights or Developer Mode on Windows and fails with EPERM otherwise.
9. **"unreadable lock file (mode 000)" changes from `skipIf(IS_ROOT)` to `skipIf(IS_ROOT || IS_WIN)`.** On Windows, `chmod 000` only sets the read-only attribute, and the file stays readable.
10. **`skipIf(IS_WIN)` on two `/proc` start-time tests:**
    - "live pid with matching start time => live; with a different start time => stale";
    - "written lock carries … this process's /proc start time".
11. **`skipIf(IS_WIN)` on two real-server tests:**
    - "second instance refuses …; SIGTERM removes the lock; SIGKILL …";
    - "SIGKILLed server seen from another hostname …".

    Both need a graceful SIGTERM/SIGINT shutdown: exit 0 and the lock released by the handlers in `src/index.ts:43-44`. On Windows, `ChildProcess.kill("SIGTERM"/"SIGINT")` terminates the process outright, so no handler runs. The first test also asserts the `/proc` start time.
12. **The `describe` "DATA_DIR not writable" changes from `skipIf(IS_ROOT)` to `skipIf(IS_ROOT || IS_WIN)`.** It depends on `chmod 0o555` on a directory (see change 2).
13. **"stale lock (dead pid / own pid / reused pid) => proceeds" drops the reused-pid case on win32 only:** `...(IS_WIN ? [] : [reusedPidCase])`. That case relies on the `/proc` start time. The dead-pid and own-pid cases still run on Windows.

Checked and left unchanged because they are already cross-platform:
- **Paths:** `os.tmpdir()` and `path.join` are used throughout. The worker's `dir + "/trade-mcp.lock"` is fine because Windows accepts `/`.
- **Line endings:** markers are matched with `"\n"`, and Node does not translate to CRLF.
- **`docs/vps-runbook.md` parsing:** it is CRLF-tolerant under `core.autocrlf` because `indexOf("\n## ")` and `[^\n]*` absorb `\r`.
- **Rename and unlink hooks:** no handles are held open during them.
- **`linkSync` onto an existing file or directory on NTFS:** gives EEXIST, as on POSIX.
- **`EADDRINUSE` listen failure:** same on Windows.
- **Heartbeat (`utimesSync`):** works the same on Windows.

## Source issues found (NOT fixed: for a developer, same branch)

### S1 (real bug; blocks every real-process CLI test on Windows): `trade-mcp/src/oauth/revoke-cli.ts:82` main guard
```ts
if (process.argv[1] && path.resolve(process.argv[1]) === path.resolve(new URL(import.meta.url).pathname)) {
```
On Windows, `new URL("file:///C:/x/revoke-cli.ts").pathname` is `/C:/x/revoke-cli.ts`, and `path.resolve` turns that into `C:\C:\x\revoke-cli.ts`. That never equals `argv[1]`. The result:
- `run()` never executes;
- `node dist/src/oauth/revoke-cli.js --force` **silently exits 0 without revoking anything**.

This also breaks on Linux and macOS when the install path contains a space or other percent-encoded character (`%20`).

Proposed fix:
```ts
import { fileURLToPath } from "node:url";
if (process.argv[1] && path.resolve(process.argv[1]) === fileURLToPath(import.meta.url)) {
```
(`src/risk/lint.ts:141` uses `pathToFileURL(argv[1]).href === import.meta.url`, which is also correct.)

Tests that stay red on Windows until S1 lands:
- tm2_35 edge:
  - "success path (in-process and real process)";
  - "--force missing";
  - "corrupt store holding real hashes";
  - "real process exit codes match in-process".
- tm2_46 edge:
  - "real CLI process: exit code 4 via process.exit on a live lock".

They are deliberately **not** skipped, because they correctly catch this bug.

### S2 (Windows liveness; the owner's request): `trade-mcp/src/datadir-lock.ts`
Current behaviour, for the record. `procStart()` (line 30) returns `undefined`, not null, when `/proc` is missing. `classify()` (lines 65-81) then skips the start-time check (line 76), so on Windows a same-host lock is **live if and only if the pid is alive**. That already fails closed: a dead pid is stale and a live pid is live.

Most of the owner's "expected 'live' to be 'stale'" failures came from the tests themselves: `sleep`/`sh` missing, `/proc` reads in `liveLock`, and the `procStart: "1"` reuse cases. Changes 3-13 fix those.

The real gap on Windows is **pid reuse**. Windows recycles pids quickly, so a crashed server's pid can belong to an unrelated live process. Its lock then looks live forever, and startup and the CLI are blocked until someone deletes it.

Proposed plan (Linux behaviour must not change):
1. In `procStart()` (line 30), add `if (process.platform !== "linux") return undefined;` before reading `/proc`. `undefined` now means "start time unverifiable on this platform", never "different start time". Do not record a Windows start time in the lock. There is no synchronous, spawn-free way to read another process's start time from Node.
2. In `classify()`, replace the block at lines 75-80 with:
   ```ts
   if (!pidAlive(info.pid)) return "stale";
   const now = info.procStart ? procStart(info.pid) : undefined;
   if (info.procStart && now !== undefined && now !== info.procStart) return "stale"; // Linux: pid reused
   if (process.platform === "win32" && Number.isFinite(ageMs) && ageMs >= LIVE_WINDOW_MS) return "stale"; // pid alive but no heartbeat for 15 s: reused pid
   return "live";
   ```
   On win32 the rule is **pid alive AND heartbeat mtime younger than LIVE_WINDOW_MS (15 s) => live**. Otherwise the lock is stale.
   - A real server refreshes the mtime every 5 s (`startHeartbeat`), so a live pid with a 15-second-old heartbeat must be a reused pid or a crashed server.
   - An unknown age (`ageMs` = Infinity, i.e. `classify()` called without an age) stays **live** on win32. That fails closed and keeps the unit test "live pid without procStart => live" passing on Windows.
   - `checkLock()` and `acquireLock()` already pass the real mtime age (lines 99, 159, 173), so no other call sites change.
   - Trade-off: a Windows server whose event loop is blocked for more than 15 s loses its lock. This is the same rule as foreign-host locks (line 73).
3. Tests after S2:
   - None of the skips above can be removed. They cover `/proc` assertions, mode bits, symlink privilege and SIGTERM semantics, which S2 does not change.
   - Edge "same-host locks ignore the heartbeat: … a live pid with an old mtime is live" (`tm2_46_datadir_lock.edge.test.ts:591`) will **fail on Windows** after S2, because the second half becomes stale there. The developer should split it:
     - keep the Linux assertion under `skipIf(win32)`;
     - add a win32-only test (`it.runIf(process.platform === "win32")`): same-host live pid with a fresh mtime is live; with mtime older than `LIVE_WINDOW_MS` it is stale and `acquireLock` replaces it.
   - Optionally, add a win32-only variant of the reuse cases ("pid reuse … is stale" in the main file and the reused-pid entry from change 13) that ages the lock past `LIVE_WINDOW_MS` and expects stale.

### S3 (minor, no change needed now)
- **`provider.ts:135`, `renameSync(tmp, oauth.json)` over an existing file.** Node uses `MoveFileExW(MOVEFILE_REPLACE_EXISTING)` on Windows, so it replaces like POSIX. It can fail with EPERM/EBUSY if antivirus, the indexer or another process holds `oauth.json` open without share-delete. If that matters, a short retry on EPERM/EBUSY is enough.
- **`datadir-lock.ts:181`, rename aside.** It renames to a fresh unique name, so there is no rename-over-existing.
- **`linkSync` on filesystems without hard links** (FAT32, exFAT, some SMB shares). It fails with EPERM/ENOTSUP. EPERM maps to `LockUnwritableError` ("not writable"), whose message is misleading. ENOTSUP is rethrown. This is low priority because production DATA_DIR is a Linux volume.
