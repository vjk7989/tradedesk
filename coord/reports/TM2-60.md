# TM2-60 report: datetime columns vs int64 math (audit)

Scope: `bt-service/vibe_bt`, `bt-service/bt_service` on pandas 3.1.1. Method: grep for every int64 / epoch conversion (`astype(int|"int64"|"i8")`, `.view`, `.asi8`, `.value`, `to_numpy(dtype="int64")`, `np.datetime64`, `.timestamp()`, `1e9`) plus every datetime-column producer/consumer (`to_datetime`, `merge_asof`, `.dt.`), then read each site. `bt_service/` has no datetime conversions (walkforward uses `datetime.date`/`timedelta` only).

Verdicts: (a) index, covered by TM2-45/42; (b) column/other, unit-safe; (c) UNIT-DEPENDENT bug.

## The (c) bug and fix (tushare_fundamentals.py)

`enrich_price_frames_with_fundamentals` crashes for any price frame whose index unit is not `us`. It is a hard failure, not a silent mis-join. Since TM2-45 loader output is ns, so real runs with `fundamental_fields` on pandas 3 hit it (existing tests only pass because their hand-built frames are `us`). Verified before the fix: index unit `us` ok; `ns` and `s` raise MergeError.

Fix: pin both keys to ns (`left["_trade_date"] = pd.DatetimeIndex(pd.to_datetime(left.index).normalize()).as_unit("ns")`; `right["_pit_date"] = pd.to_datetime(right["_pit_date"]).dt.as_unit("ns")`). Values identical (as_unit is lossless; no-op on pandas 2.3). After the fix `us`, `ns`, `s` all give `[nan, 42.0, 42.0]`. The returned frame keeps the caller's original index (`merged.index = original_index`).
