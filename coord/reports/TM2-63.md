# TM2-63 report
Change: trade-mcp/src/index.ts only. SIGINT/SIGTERM `stop` is registered right after acquireLock()/exit hook, before heartbeat, createHttpServer and listen. stop() is idempotent, stops the heartbeat if started, closes http only when listening (else exits 0 directly), exit 0 so the exit hook releases the lock.
Probe (10x SIGTERM at spawn, 10x at first stderr line): first-line 10/10 exit 0, lock removed; at-spawn 10/10 exit null/SIGTERM with no lock file (signal lands before JS runs / before acquireLock, so nothing to release; unavoidable in-process).
vitest: 2522 passed, 1 failed (tm2_46 SIGKILLed-hostname test, times out because its sigtermReady preload waits for a newListener marker AFTER the started line; the handler now registers earlier. Expected; test writer removes the preload). tsc and build clean. smoke 18/18.

## Review
Verdict: APPROVE (no blocking findings). Reviewed trade-mcp/src/index.ts and this report. `npm ci`, `tsc --noEmit` and `npm run build` are clean. Real-process probe on dist: 8x SIGTERM and 8x SIGINT at the first stderr line all exit 0 with the lock removed; 10x SIGTERM at spawn all exit null/SIGTERM.

1. index.ts:32-49 and 50-53, stop in every phase (not blocking, correct).
   - main() runs synchronously from acquireLock to listen(), so a signal is only dispatched at the await, or before main starts. There is therefore no moment where the lock is held and no handler is registered.
   - Before the heartbeat: `heartbeatStop?.()` is a no-op, http is undefined, so `process.exit(0)`.
   - After the heartbeat, before listen: stop clears the interval and exits 0.
   - Listen pending: `http.listening` is `!!_handle`. For an IP host the handle is bound synchronously, so it is true and the close plus closeAllConnections path runs. For a hostname that needs a DNS lookup the handle is null, nothing is bound, and exit(0) leaves no half-bound socket (the kernel closes any fd on exit). No cleanup is skipped, because the only state is the lock (exit hook) and the heartbeat (cleared).
   - After listen: unchanged behaviour.
   - Idempotence: the `stopping` flag makes a second signal a no-op. Nothing in stop can throw: clearInterval, `.listening`, close and closeAllConnections do not throw on a bound server.
   - Lock: released through `process.on("exit", releaseLock)` in every path, including process.exit(0).
2. index.ts:54, normal path (not blocking). The started log text is byte-identical, and exit code on stop is still 0. The --stdio branch returns before this code, so stdio mode is untouched. The only behavioural change is that handlers now exist earlier. The `started` line is now printed after the handlers exist, which is the intended guarantee.
3. Windows (not blocking). src has no POSIX-only assumptions. `process.on("SIGINT"/"SIGTERM")` is fine on Windows. `process.kill(pid,0)` in datadir-lock.ts:42 works on Windows. `/proc` use at datadir-lock.ts:31 is guarded by `process.platform !== "linux"`. chmodSync in oauth/provider.ts:146 is a no-op-ish call and does not throw. No SIGHUP/SIGUSR, shell or fork usage.
4. AC "SIGTERM at spawn exits 0" (not blocking, finding is that the developer is right). A signal that arrives before Node has installed any JS handler gets the default action, which is exit by signal (code null). I reproduced it: 10/10 null/SIGTERM. The window ends before module load and main(), so the lock has not been acquired and there is nothing to leak.
   - No realistic in-scope mitigation exists. Entry-file code cannot run earlier than Node bootstrap. A tiny wrapper script (`bin` shim, tini or `docker --init`) would only move the same window to the wrapper, and it would change the process/PID model that the lock (pid + /proc starttime) relies on. Cost and risk are not worth it.
   - Recommend amending the AC to: "SIGTERM at spawn leaves no lock; SIGTERM at first stderr line exits 0 and removes the lock". The test writer should assert exactly that (code null or 0 and no lock for at-spawn; code 0 for first-line).
5. tm2_46 test (not blocking for src; blocking for merge of the PR as a whole until fixed). test/tm2_46_datadir_lock.edge.test.ts:791-810 and :952 wait for a sigtermReady marker emitted after the started line. With handlers now registered earlier, the marker semantics no longer hold, and the test times out. The source behaviour is correct (stop is registered before the started line). It is a test issue for the test writer: drop the preload (SIGTERM_READY_PRELOAD, the `opts.sigtermReady` branch, and the `lastIndexOf(SIGTERM_READY) > i` wait) and fix the "second instance refuses" SIGINT race the same way (send the signal after the started line). Also add the planned tm2_61_shutdown_order test.
6. index.ts:41-45, minor (not blocking). While close is pending (a connection that closeAllConnections cannot drop), a second signal is a no-op, so the process can only be stopped with SIGKILL. This is within the brief ("no-op or immediate exit 0"). Optionally make the second signal `process.exit(0)`.
7. index.ts:53, minor, pre-existing (not blocking). A listen error (EADDRINUSE) emits an unhandled 'error' event and crashes with exit 1. The exit hook still releases the lock. Not part of this task.
