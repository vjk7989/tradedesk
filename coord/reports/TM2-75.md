## Approach
Option (a): SQLite online backup API inside paper-bot (`docker compose exec -T paper-bot python -c ...`, stdlib `sqlite3`; image is python:3.12-slim, so no image change). paper-bot opens paper.db with `journal_mode=WAL`, `busy_timeout=5000` (paper_bot/db.py:24-25), path `/data/paper.db` (DATA_DIR). Output: `paper_bot_data.db` in the backup (plain snapshot, integrity-checked, covered by MANIFEST). Bot is not interrupted.
- Bot not running: one-off `compose run --rm --no-deps -T paper-bot` with the same snapshot (consistent, replays leftover WAL; a file copy would lose it). Any failure exits non-zero and the partial dir is cleaned, as for existing volumes.
- Restore: if `paper_bot_data.db` present: stop paper-bot if running (`docker ps` name filter, no compose, so the existing "--force skips compose probe" test holds), remove paper.db/-wal/-shm, copy snapshot to paper.db (600, chown 10001:10001), start the bot if it had been running.
- Existing volumes' code path, naming and output format unchanged; `paper_bot_data` appended to the end of `VOLUMES`, skipped in the tar loop via `SNAPSHOT_VOL`.

## Review
Verdict: CHANGES REQUESTED (one blocking item; everything else non-blocking).

1. BLOCKING, deploy/restore.sh:72-73 (restore data-loss window). `rm -f paper.db ...` runs before `cp`, in one `sh -c`. If cp fails (disk full, bad snapshot path) the old paper.db is gone, and with `set -e` the bot (already stopped at line 71) is left stopped. Copy to `/dst/paper.db.new`, chown/chmod, then `mv` over paper.db and rm the -wal/-shm; and run `PRAGMA integrity_check` on the snapshot (MANIFEST only proves the hash) before stopping the bot. On failure, restart the bot if it was up.
2. Non-blocking, deploy/backup.sh:20-33 vs 76-84. `${COMPOSE[@]}` has no `-p "$PREFIX"`. The volume loop uses `${PREFIX}_vol`, but compose derives the project from the deploy dir name when COMPOSE_PROJECT_NAME is unset. It matches by default ("deploy"). With a TRADEDESK_DEPLOY_DIR named differently, `ps` finds nothing and `run` mounts a different, empty `<dir>_paper_bot_data` volume. It then fails loudly (db missing, non-zero exit) rather than silently. Add `-p "$PREFIX"`.
3. Non-blocking, backup.sh snippet. The whole snapshot is read into memory in the container (256m mem_limit, shared with the live bot) and written to stdout. Fine for now, and a temp file in /tmp leaks if stdout write fails. Stream in chunks and put the removal in a `finally`.
4. Non-blocking, shellcheck. SC2034 for EXCLUDED_VOLUMES (read by the guard test, so expected). SC2086 on `docker stop/start $was_up` (intentional splitting, add a disable comment). bash -n OK on both.
5. Non-blocking, docs/backup.md:73-75. Line wrapping is ragged (long line). "otherwise `up -d` starts it" is accurate only when restore is run without --force and no containers exist; consider saying so.

## Fix round 1
1. restore.sh: verify-then-swap. `PRAGMA integrity_check` on the snapshot first, in a one-off `python:3.12-slim` container (stdlib sqlite3, read-only mount, `immutable=1`; chosen because host python/sqlite3 cannot be assumed). Then stop the bot, copy to `paper.db.new`, chown 10001:10001, chmod 600, `mv -f` over `paper.db`, only then rm -wal/-shm. An EXIT trap (fires under `set -e`) removes `paper.db.new`, restarts the bot if it was up, and exits with the original status; the old db is untouched.
2. backup.sh compose calls now use `-p "$PREFIX"`. Volume tar loop unchanged.
3. Snapshot snippet streams in 1 MiB chunks; temp file removed in `finally`; integrity check kept. Re-run for real against a WAL db (20000 rows, -wal present, writer inserting during the backup): exit 0, 20050 rows, no temp file left.
4. shellcheck disables added (SC2034 on EXCLUDED_VOLUMES, SC2086 on `$was_up`) with reasons. shellcheck itself is not installed here.
5. docs/backup.md: rewrapped; documents verify-then-swap, the trap, the `-p` fix, and that `up -d` is needed only when the stack was down (no `--force`).

Verification: `bash -n` OK on both. `pytest -q deploy/`: 5 failed, 342 passed, 23 skipped, 25 errors = the 3 docker-less compose-config failures plus 25 errors that also occur on clean main, plus the 2 expected file-set tests (test_layout_and_manifest, test_dest_with_spaces_backup_and_restore) for the test writer.
