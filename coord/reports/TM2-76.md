## Design
- **Indexes** (`CREATE INDEX IF NOT EXISTS`, run in `connect()`, so a live DB migrates on its next start): `decisions(symbol,ts)`, `decisions(action,ts)` as the brief asks, plus `decisions(symbol,id)`, `decisions(action,id)`, `trades(ts,symbol)`, `equity(ts)`. Finding: the planner never picks the `(.., ts)` indexes for the dashboard/CSV queries, because they all `ORDER BY id DESC` and the `(.., ts)` entries are not in id order. The `(.., id)` indexes are what make the filters fast and what keyset pagination (`id < ?`) uses. The `(.., ts)` ones are kept as the brief asks (time-range queries) but are not what makes it fast.
- **`PRAGMA optimize`** at connect (startup) and after each maintenance run. **No VACUUM anywhere.**
- **Daily maintenance** (`db.maintain`): in the existing `web.loop`, right after a tick, via `asyncio.to_thread` on the same writer connection, so it is never concurrent with a tick (the writer connection is single-thread by design). Gated by `state.last_maintenance` (24 h). Exceptions are logged and never stop the loop. Downsampling commits in batches of 168 hours, so the write lock is held briefly.
- **Decisions are never deleted.** Pagination: `GET /api/decisions?limit=&before=<id>` (default limit 200, max 1000 as before; `before` in [1, 2^63-1], invalid gives 422 exactly like the existing `limit` validation). Dashboard `/?before=<id>&limit=` validates like the filters: invalid values silently fall back to the default (page 1, 200). An "older decisions" link (carrying symbol/action filters) appears only when an older page exists. Without the params the output is unchanged (TM2-72's tests pass; the heading still says "latest 200"). The CSV routes stay full exports (audit trail), no pagination.
- **Dashboard trades table** now shows the latest 500 trades with a note linking `trades.csv` when truncated (otherwise unchanged). Reason: it rendered every trade ever, which alone broke the 300 ms goal (9.4k trades). `/api/trades` and `trades.csv` still return all.
- **Speed-ups with identical output**: `summary()` scans only `total` plus the last row instead of every equity column; `per_symbol` groups trades once instead of one scan per symbol (same id-order sums); `/api/equity` and `/api/trades` build the same compact JSON without the per-row FastAPI encoder.

## Equity downsampling
Rows older than `EQUITY_DETAIL_DAYS` (default 30, cutoff floored to a whole hour so a partial hour is never touched) are thinned per hour to the **first, last, max, min and the hour's best drawdown pair (peak and trough)**: at most 6 rows per hour (5 minute data has 12). Hours with <= 6 rows, hours containing a NULL total, and hours whose ids are interleaved with another hour (clock jump) are left alone. Every batch runs in `BEGIN IMMEDIATE ... COMMIT` and rolls back on any error. Idempotent: a kept hour has <= 6 rows, so a second run finds nothing (verified: 0 rows deleted, 10 ms scan).

### Why first/last/max/min is not enough (deviation from the brief)
Counterexample, one hour `100, 120, 90, 130, 95, 99, 101`: first 100, last 101, max 130, min 90. Dropping 120 and 95 leaves the series `100, 90, 130, 101`; true max drawdown is (130-95)/130 = 26.9%, the 4-point version gives 22.3%. The brief's recipe is therefore not exact, and the intra-hour pair is what fixes it.

### Proof of exactness
`max_drawdown` (stats.py) is the max over t of (peak_t - x_t)/peak_t with peak_t the running max (the capital is prepended; only peaks > 0 count). Equivalently, MDD = max over pairs i <= j of f(i,j) = (x_i - x_j)/x_i with x_i > 0: the running peak at j is >= x_i, which only makes the ratio larger, and the maximising i is itself the running peak. So MDD is the best "buy high, then sell low" pair in time order.
Split the pairs by hours (H_a < H_b) :
1. Cross-hour pair, i in H_a, j in H_b: for fixed j, f is increasing in x_i, so the best i is the maximum of H_a (kept); for fixed i, f is decreasing in x_j, so the best j is the minimum of H_b (kept). (The capital is an earlier point, handled the same way.)
2. Same-hour pair: the hour's best pair is computed by the same running-peak scan and both its points are kept.
Hence the optimal pair of the full series is a pair of kept points, and any pair of kept points is a pair of the full series, so the max over kept points equals the max over all points. The kept-series scan evaluates the identical operands `(p - x)/p`, so equality holds bit for bit, not only mathematically. Final equity: the last row of the last hour is always kept (and the latest hour is inside the detail window anyway). Min/max equity (chart range) are kept as well. Rows keep all of their columns (cash, unrealised, total).

Findings
1. **BLOCKING - paper-bot/paper_bot/web.py:147 (`page_params`).** `before.isdigit()` is true for Unicode digits such as `²`, but `int('²')` raises ValueError, so `GET /?before=%C2%B2` returns 500. The brief says the dashboard ignores bad values. Fix: use `before.isascii() and before.isdigit()` (same for `limit`), or try/except around `int()`. (Non-ASCII digits such as Devanagari `२` currently parse as 2 and are accepted, which is harmless but goes away with the same fix.)
2. Downsampling correctness - verified, no defect (db.py:57-107). The proof holds for cross-hour pairs (peak hour's max and trough hour's min are kept), for same-hour pairs (the kept peak/trough pair), for peak in an earlier hour with the trough in a later one, and for the capital prepended in stats.max_drawdown. My independent generator (30,000 seeds; walk/ties/spike/integer/zero-floor modes; hours with 1,2,3,6,7,8,12,<=30 rows; skipped hours; non-aligned start; cutoff landing inside the data; batch size 1, 3, 168) compared `stats.max_drawdown([capital]+totals)`, final, min and max before and after: 0 mismatches, and a second run deleted 0 rows every time. The one assumption is positive equity (f(i,j) is increasing in x_i only when x_j > 0); equity <= 0 is not a paper-bot state, and 0 floors passed in my tests. Ties are fine (index() picks the first, the strict `>` keeps the first peak). Single-row and <=6-row hours are untouched. The cutoff is floored to a whole UTC hour (epoch arithmetic, no timezone), so the hour containing the cutoff is never partially thinned. A float on the exact hour boundary that lands in a different bucket than the range select fails the contiguity check and is skipped (safe).
3. Crash safety - OK (db.py:93-107). Each batch is BEGIN IMMEDIATE/COMMIT of whole hours with ROLLBACK on any BaseException; each committed state is itself drawdown-exact, so a crash between batches is harmless. `last_maintenance` is set only after the work, so a failed run retries on the next tick (non-blocking: it will log the exception every 5 min until fixed). A NULL `ts` would make `h*HOUR` raise TypeError and abort that maintenance run on each tick (non-blocking, NULL ts is not produced by the engine).
