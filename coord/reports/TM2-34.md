## Failure groups

All 80 failures have one root cause: datetime/timedelta resolution (ns vs us). pandas 3 infers `us`
for `pd.Timedelta(n, "min")`, string-parsed Timedelta/Timestamp, and `DatetimeIndex` built from Timestamps,
where pandas 2 always gave `ns`. The tests hard-assert `ns` units / dtypes.

### 1. Timedelta unit (22 = 12 + 10)
- `tests/test_tm15_warnings_edge.py::test_target_equals_old_timedelta_value_and_ns_unit[5m]` (x12: 1m,3m,5m,10m,15m,30m,1h,4h,1d,1D,1H,4H). Test compares `pd.Timedelta(rule)` (now `us`) to a `ns` Timedelta.
- `tests/test_tm8_edge.py::test_timeframe_delta_equals_old_value[5m]` (x10: 1m,3m,5m,15m,30m,1h,4h,1d,1w,1M). `new.unit` is `us`, test wants `ns`.
- Source sites: `vibe_bt/backtest/loaders/ccxt_loader.py:38-49` (`_TIMEFRAME_DELTA`, `pd.Timedelta(n, "min")` etc.), used at `ccxt_loader.py:513-518` for a tolerance compare (value-equal across units, so behaviour is unchanged). `vibe_bt/backtest/loaders/local_loader.py:131` already pins `unit="ns"` and passes.
- Fix: S. Either `.as_unit("ns")` on the constants or relax the tests to compare `.value`/`total_seconds()` and drop the unit assertion. Behaviour is not affected.

### 2. Resample index dtype (57 = 33 + 12 + 12)
- `tests/test_tm15_warnings_edge.py::test_resample_irregular_gaps[5m-UTC]` (33 cases, intervals x {None, UTC, Asia/Kolkata}), `::test_resample_single_row[5m]` (12), `::test_one_second_finer_source_is_resampled[5m]` (12).
- Message: `Attribute "dtype" are different [left]: datetime64[us, UTC] [right]: datetime64[ns, UTC]`. The production result keeps the input's unit (`us`, since the test builds `DatetimeIndex([Timestamp(...)])`); the independent expectation `_expected` (tests/test_tm15_warnings_edge.py:101-120) is built via ns arithmetic and so is `ns`.
- Source sites: `vibe_bt/backtest/loaders/local_loader.py:131-156` (`df.resample(rule[, origin=anchor]).agg`), same pattern `yfinance_loader.py:239`, `yahoo_loader.py:271` (`resample("4h")`), `loaders/base.py:349-395` (`resample_bars`, PeriodIndex route, re-stamps from the original index so unit follows the input).
- Fix: S-M. Decide the policy: normalise bar indexes to one unit at the loader boundary (recommended: `as_unit("ns")` in the loader output / `resample_bars`) or make tests unit-agnostic (`check_index_type`/cast expected to the output's unit). The policy decision matters more than the edit.

### 3. Warning-capture harness (1)
- `tests/test_tm15_warnings_edge.py::test_capture_mechanism_sees_generic_timedelta_warning`: asserts that `pd.Timedelta('3min')` emits NumPy's "'generic' unit" warning in a subprocess. pandas 3 no longer does, so the premise is gone. Fix: S, delete or xfail the test (it guards a pandas 2 only deprecation).

### 4-7. Zero failures
Offset alias removals (`H`, `T`, `M` etc.): tests parametrize `1H`/`4H`/`1D` and `to_offset` in `vibe_bt/backtest/rebalance_mask.py:10,23,61,88`; these pass on 3.1.1. Copy-on-write, string dtype and removed APIs gave no failures in the suite.

## Warnings seen (not failures; 8 total)
- `Pandas4Warning: DatetimeIndex.dayofweek is deprecated` (use `day_of_week`): `tests/test_crypto_backtest.py:97,100` (test code only; no `dayofweek` in `vibe_bt`/`bt_service`).
- `Pandas4Warning: DatetimeIndex.values returning an ndarray that drops timezone information is deprecated` (pandas 3.1): raised from tz-aware runs in `test_intraday_edge.py` (x2), `test_p92_edge.py` (x2), `test_tm8_edge.py` (x1). Source: `vibe_bt/backtest/engines/base.py:232` (`dates.values` in `searchsorted`) and `:298` (`dates.values.view("i8")`). Pandas 4 change: this will return a DatetimeArray. Fix: `dates.tz_convert(None).to_numpy()` / `dates.asi8` (M, see below).
- `StarletteDeprecationWarning` (httpx in TestClient): unrelated to pandas.

## Latent risk not caught by tests
`engines/base.py:298` `dates.values.view("i8")` and `rebalance_mask.py:67,95` (`asi8`, already `as_unit("ns")`) compare int64 epochs. If panel indexes of mixed units (ns vs us) are merged, int views are not comparable. The suite passes because inputs share a unit within a run, but a unit-mixing loader (e.g. one loader returning `us`, another `ns`) would silently mis-align. Mitigation is task P3-B below.

## Recommendation
Upgrade is cheap and low-risk for behaviour: 0 production-path failures and a single root cause. But there is no feature need and bt-service is pinned `pandas<3` by choice, and pandas 3.1 already emits `Pandas4Warning`s that need clearing. Recommended: stay on 2.3.x until the unit policy (P3-A) and the `.values` cleanup (P3-B) are merged on 2.x (both are compatible with 2.x), then lift the pin in one small PR (P3-C). Event trigger: do P3-C when a dependency or the Python/numpy upgrade requires pandas 3, or after P3-A/B land, whichever is first. No calendar date is needed since the pre-work is forward compatible.
